# 公定／參考格式表單的欄位 mapping

> ACTIVE｜2026-09-20（廠商驗收修正 C 包）。單一定義在程式 `src/lib/officialForms.js`；本檔是它的人可讀版本，
> 由 `src/lib/officialForms.test.js` 逐列釘住——程式改了欄位而本檔沒改（或反過來）測試就紅。

## 為什麼有這份文件

2026-09-20 的廠商驗收退回一條 P0：**廠商的編輯畫面和紙本不是同一張表**。舊做法是廠商先填一份精簡表
（`DailyLogFields`），要另外切「公定格式檢視」才看得到真表；紙本 renderer 只服務唯讀與列印。兩份各自定義欄位，
於是「畫面填得完、紙上還是空的」這類落差無法從程式上排除。

C 包的做法是把欄位定義收成一份：

* **一份 mapping**：原表欄名 → 儲存欄位 → 來源／計算 → 可編角色 → 必填／不適用條件 → 紙本位置（本檔各表）。
* **一張紙**：紙本元件同時是編輯畫面。給了 edit context 就在原表的格子裡長出輸入框（哪一格誰可編由 mapping 決定），
  沒給就是純文字——列印／PDF 與唯讀視角走的是同一個元件、同一份資料。
* **一套來源呈現**：AI 或紙本抄錄帶進來的值本來就在格子裡，旁邊一枚輕量狀態章；點「原文」回看
  `field_sources[].evidence` 的紙上原文與原照片（B 包已經寫進來的那一份，不另建一套）。

規則（畫面與紙本都要做到）：

1. 標示一律是「參考工程會／臺北市格式」，並印出範本鍵與版本；**不得**出現「機關核定」「正式表單」之類字樣。
2. **版面參考與工程技術標準分離**：臺北市範例檔裡的示例數值（如保護層 4cm／4.5cm）、良好與不良填寫示例、
   假公司名與示例判定一律不入產品。檢查項目與檢查標準只取本案核定的檢查表範本；沒有就待補。
3. 工程會 PDF 的附件直接下載網址保存在 [pcc-sources.json](../reviews/assets/2026-09-20-contractor-acceptance/pcc-sources.json)。

## 簽署版本的語意保存

存檔時把當時的表單範本鍵與版本寫進文件內容（`content.form_template = { key, version }`，
`officialForms.stampFormTemplate`）。版本內容與內容雜湊本來就不可變，加上這個戳記之後：

* 舊文件印出來時，頁首標的是**它自己當時的範本版本**，不是現在的；
* 之後改範本（加欄位、改欄名）不會改變舊簽署版本的內容或判定；
* 判定類欄位（自主檢查的檢查結果）仍由伺服器在簽署交易內以當時的範本重算並落庫，畫面只是預覽。

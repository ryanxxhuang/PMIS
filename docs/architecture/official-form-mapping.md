# 公定／參考格式表單的欄位 mapping

> ACTIVE｜2026-09-20（廠商驗收修正 C 包建立、C2 包補齊四份）。單一定義在程式 `src/lib/officialForms.js`；
> 本檔是它的人可讀版本，由 `src/lib/officialForms.test.js` 逐列釘住——程式改了欄位而本檔沒改（或反過來）測試就紅。
> 四份：施工日誌（工程會附表四）、自主檢查表（臺北市）、監造查驗紀錄表（臺北市施工抽查紀錄表）、
> 監造報表（工程會附表五，**按日**填報的日報，不是監造月報）。

## 為什麼有這份文件

2026-09-20 的廠商驗收退回一條 P0：**廠商的編輯畫面和紙本不是同一張表**。舊做法是廠商先填一份精簡表
（`DailyLogFields`），要另外切「公定格式檢視」才看得到真表；紙本 renderer 只服務唯讀與列印。兩份各自定義欄位，
於是「畫面填得完、紙上還是空的」這類落差無法從程式上排除。

C 包對廠商的兩份（施工日誌、自主檢查表）、C2 包對監造的兩份（監造查驗紀錄表、監造報表）做同一件事——
把欄位定義收成一份：

* **一份 mapping**：原表欄名 → 儲存欄位 → 來源／計算 → 可編角色 → 必填／不適用條件 → 紙本位置（本檔各表）。
* **一張紙**：紙本元件同時是編輯畫面。給了 edit context 就在原表的格子裡長出輸入框（哪一格誰可編由 mapping 決定），
  沒給就是純文字——列印／PDF 與唯讀視角走的是同一個元件、同一份資料。
* **一套來源呈現**：AI 或紙本抄錄帶進來的值本來就在格子裡，旁邊一枚輕量狀態章；點「原文」回看
  `field_sources[].evidence` 的紙上原文與原照片（B 包已經寫進來的那一份，不另建一套）。

C2 包把 `InspectionFormFields`／`SupervisorLogFields` 兩份精簡表刪掉，改由 `InspectionFormSheet`／`SupervisorLogSheet`
同時當編輯畫面與列印版面；隨之退場的還有只服務那兩份精簡表的 `ChecklistItemsTable`／`FieldSourceChip`／`RowsEditor`。

規則（畫面與紙本都要做到）：

1. 標示一律是「參考工程會／臺北市格式」，並印出範本鍵與版本；**不得**出現「機關核定」「正式表單」之類字樣。
2. **版面參考與工程技術標準分離**：臺北市範例檔裡的示例數值（如保護層 4cm／4.5cm）、良好與不良填寫示例、
   假公司名與示例判定一律不入產品。檢查項目與檢查標準只取本案核定的檢查表範本；沒有就待補。
3. 工程會 PDF 的附件直接下載網址保存在 [pcc-sources.json](../reviews/assets/2026-09-20-contractor-acceptance/pcc-sources.json)。

## 簽署版本的語意保存

存檔時把當時的表單範本鍵與版本寫進文件內容（`content.form_template = { key, version }`，
`officialForms.stampFormTemplate`）。版本內容與內容雜湊本來就不可變，加上這個戳記之後：

* 舊文件印出來時，頁首標的是**它自己當時的範本版本**，不是現在的；
* 之後改範本（加欄位、改欄名）不會改變舊簽署版本的內容或判定；
* 判定類欄位（自主檢查的檢查結果）仍由伺服器在簽署交易內以當時的範本重算並落庫，畫面只是預覽。

## 3. 監造查驗紀錄表（臺北市「施工抽查紀錄表」格式參考範例）

可編角色是**監造**，不是廠商。「實際抽查情形」「判定」「本次確認數量」都是監造親自填的，
而且本次確認數量簽署後會寫進監造確認紀錄、成為廠商可估驗的依據——所以格內編輯**只是呈現與輸入**，
伺服器 `field_document_sign_inspection_form_internal` 的驗證一律照舊、一條都沒放寬：
單位須等於標單工項單位、階段須在該工項檢驗停留點的必要階段（H 點）之內、申報量須與查驗申請相同、
本次確認量不得超過申報量、判定與數量須一致（合格＝申報、部分合格 0<x<申報、不合格＝0）、
同一查驗已有有效確認量時改量須先撤銷（`PD008`）、被標 `filled` 未確認的欄位簽署會被 `PD004` 擋下。
畫面上的 `inspectionFormIssues` 只是同一條規則的即時預覽，伺服器才是邊界。

| 契約變更次數 | 有：`change_orders` 的已核准件（與估驗、S 曲線同一份資料） | **確定性計算**：截至本日已核准的件數；沒有變更日期的已核准件仍計入並在來源註明。資料未載入時印「待補」，不印 0 |

**原表沒有、本系統加上的格**：監造到場人員與時段。原表註 3 明寫「本監造報告表格式僅供參考，各機關亦得依契約約定事項，
自行增訂之」，所以增訂是原表允許的；紙上仍標「（本系統欄位，非附表五原表欄位；依原表註 3 各機關得自行增訂）」，
而且它只能由監造親自填寫並按「確認到場人員」才算數（鏡像 DB `needs_confirmation`；任何照片都不是到場證明）。

## 5. 四份共同的規則

* **內容是 JSONB，四份都零 migration**：C／C2 補的原表欄位全部是 `field_document_versions.content` 的新鍵，
  不動 schema。事實表（`daily_logs`／`supervisor_logs`／`checklist_records`／`inspections`）是衍生的報表列，
  權威內容永遠是被簽署的那個版本；新鍵不進事實表不影響判定與計價。
* **可編角色只由 mapping 決定且 fail-closed**：`isEditableBy(docType, key, org)` 查不到的鍵一律不可編；
  `canEditForm(docType, org)` 為假時連「加一列／移除一列」這種結構動作都不長出來。伺服器 RLS／RPC 仍是安全邊界。
* **「沒有來源列」不等於「待補」**：待補章只在待補清單說它待補、或來源自己是 `pending` 時才出現，
  原表有但本系統列為非必填的格（表報編號、展延天數、契約金額…）不會長出誤導的「待補」。
* **列印不印任何狀態章**：`showMarks` 只在有 edit context 時為真；列印頁與 PDF 是同一個元件的純文字輸出。

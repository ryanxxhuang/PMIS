### 1.4 本次盤點發現的既有缺陷與限制

1. **估驗「待廠商請款」導向錯頁**：`ballInCourt.js:74` 只有 `who === 'owner'` 才導 `/payments`，廠商的「待廠商請款」被導到 `/valuation`，但填請款日的欄位在 `/payments`。
2. **Agent 溢位連結指向內容不同的頁**：`Agent.jsx:62` 的「還有 N 件，到提醒中心看全部」連到 `/alerts`，但 `/alerts` 不含送審、疑義、查驗、觀察、變更；溢位的那幾件多半在該頁找不到。
3. **`/alerts` 完全不分角色**：所有人看到同一份清單（含球不在自己手上的缺失、請款）。
4. **Dashboard 行動中心溢位無出口**：`Dashboard.jsx:391` 只寫「還有 N 項…」純文字，沒有連結。
5. **初始化第 3 步完成條件與 D-014 不一致**：`Dashboard.jsx:60` 仍是「待審歸零且至少核定一筆」，D-014 已改為「AI 整理完成即可」。**屬 W8-3A，本包不動**，此處僅登記落差。
6. **契約義務責任方與操作權不一致**：`Contract.jsx` 的狀態按鈕只在 `can.edit` 時出現；正式模式的監造／機關即使被標成責任方，也不能在該頁完成。**屬契約工作頁與權限語意，W8-2B 不改 `Contract`／RLS，也不得把這些列成 `mine`。**

## 2. Agent 與 Dashboard 重複顯示的內容

### 2.1 完全重複：同一份資料、同一段程式、兩頁各畫一次

| 內容 | Dashboard | Agent | 是否同源 |
|---|---|---|---|
| 球在我手上的協作項清單 | `RoleActionCenter`（`Dashboard.jsx:357`），標題依角色為「待你送出／改善」「待你審核」「待你核定／撥款」，上限 8，溢位無連結 | `MyItemsCard`（`Agent.jsx:43`），標題「今日待我處理」，上限 8，溢位連 `/alerts` | **是**：兩邊都呼叫 `myOpenItems(org, …)`，輸入資料相同 |

這是 W8-2 要解決的核心重複：同一份 `myOpenItems`，兩個標題、兩個上限行為、兩種溢位出口。

### 2.2 同一份計算被算兩次（顯示不重複，但成本與漂移風險重複）

`Dashboard.jsx:129-152` 與 `assistantData.js:20-40` 各自實作相近的進度與財務計算（`buildBillableTree`→`buildCumMap`→`totalCumAmount`、`plannedNow` 線性內插）。數字目前大致一致，但兩者的日期 memo 依賴不同：Dashboard 有 `todayISO`，`useAssistantData` 只有 `progressPlan`，長開分頁跨日可能保留舊的 `plannedNow`。

這是既有重複與潛在漂移，但**不屬今日待辦與 Agent 去重的必要改動**。W8-2B 不讓 Dashboard 依賴 Agent 專用的 `useAssistantData()`，也不順手重構進度計算；要整理時另以小型純函式與日期回歸測試處理。

### 2.3 Agent 專屬、不重複（應維持）

- `DraftInboxCard`（`agent_actions` 待覆核草稿）：只在 `/agent`，Dashboard 沒有。**依硬限制，本包不得把它搬進今日待辦。**
- 對話區（`CopilotChat` + `runAgent`）。
- 浮動 Copilot（`CopilotFab`）：同一 Agent 的新對話，不含任何待辦清單，無重複。
- W8-2B 移除 Agent 內的完整清單後，只保留無件數的「前往今日待辦」連結；不讓 Agent 為顯示一個可能漂移的數字再載入完整待辦聚合。

### 2.4 Dashboard 專屬、不重複（但與待辦語意衝突）

- `InsightsPanel`（`aiInsights.js`）：註解已宣告「同一份 insights 只在 Dashboard 出現」，確實沒有在 Agent 重複。但其 7 條規則中有 5 條**在語意上重複了真待辦**：
  - 缺失逾期未結案 ↔ 行動中心的「缺失」
  - 契約義務逾期／即將到期 ↔ `/alerts` 的「契約」
  - 已請款未收款 ↔ 行動中心的「估驗（待機關撥款）」與 `/alerts` 的「收款」
  - 變更設計待核定 ↔ 行動中心的「變更」
  - 試體逾期未試驗 ↔ `/alerts` 的「試驗」
  只有「進度落後」與「澆置未取樣」是行動中心沒有的。

### 2.5 「球權判斷」目前有三套實作

| # | 實作 | 涵蓋類型 | 有到期日／排序 | 使用者 |
|---|---|---|---|---|
| A | `src/lib/ballInCourt.js` | 疑義、送審、估驗、變更、缺失、查驗、觀察 | ✗ | Dashboard、Agent、`assistantFacts.待我處理` |
| B | `supabase/functions/_shared/agentTools.ts` `collectOpenBallItems` | 缺失、送審、疑義、估驗、**契約義務** | ✓（`due_date`／`overdue_days`＋依到期排序） | `list_my_open_items` 工具、`send-reminders` 每日信 |
| C | `src/pages/web/Alerts.jsx` 內嵌 | 契約義務、缺失、試體、請款／收款、驗收、ITP | ✓（分 overdue／soon／todo） | `/alerts` |

**A 與 B 的類型集合互不包含**：A 多了查驗、觀察、變更；B 多了契約義務。同一個使用者在網頁看到的待辦，和 Agent 工具／每日提醒信說的待辦不是同一份。C 又是第三套規則，且完全不看球權。

另有一個不可複製到新前端的既有問題：B 對 `contract_obligations.responsible` 採「無法辨識就歸廠商」，因此 `null`、`其他` 或未知文字都可能誤入廠商 Agent／早報。W8-2B 的前端聚合只接受「廠商／監造／機關」三個精確值；其餘維持未指定。伺服器端一致性另行登記，不在本次前端包順手修改。

## 3. 三分類：現在輪到我／等待對方／今天已完成

### 3.1 現在輪到我（球權＝登入角色，且有唯一完成動作）

| 角色 | 可產生的待辦類型 | 目前是否已在 Dashboard |
|---|---|---|
| 廠商 | 估驗草稿送審、已核定待請款、送審退回補正、疑義已回覆待結案、缺失開立／改善中、觀察待處理、**試體齡期到期**、**ITP H／W 未叫驗**、**`responsible='廠商'` 的契約義務** | 前 6 類有；後 3 類只在 `/alerts` |
| 監造 | 待查驗、估驗待核定、送審待審定、疑義待回覆、缺失待複查、變更待審查、觀察（`assigned_to='supervisor'`）、**竣工確認／複驗** | 前 7 類有；驗收階段期限只在 `/alerts` |
| 機關 | 估驗待撥款、變更待核定、**驗收法定期限（竣工確認／初驗／複驗／正式驗收／結算驗收證明書）** | 前 2 類有；驗收期限只在 `/alerts` |

監造／機關責任的契約義務不進 `mine`：責任描述雖存在，但目的頁沒有該角色可完成的操作。W8-2B 只讓它們留在 `/contract` 契約清單中，不包裝成待辦；這項落差留待 W8-3B 的契約重點／工作頁處理。

### 3.2 等待對方（我是關係人，但球不在我手上）

可完全由既有 `myOpenItems` 的補集推導，不需要新資料：對本案所有未結項取 `ball.who !== 我的 org`，並以球權方分組。建議只列與登入角色有直接對手關係的類型，例如：

- 廠商看：送審待監造審定、估驗待監造核定／待機關撥款、疑義待監造回覆、缺失待監造複查、變更待監造／機關核定。
- 監造看：缺失待廠商改善、送審待廠商補正、疑義待廠商結案、變更待機關核定。
- 機關看：估驗待廠商送審／請款、缺失待廠商改善、送審待監造審定。

三套資料都已存在於 store，沒有任何新查詢。

### 3.3 今天已完成（第一版只使用可靠操作時間戳）

| 想顯示的事件 | 可用欄位 | Demo 引擎 | DB 引擎 | 判定 |
|---|---|---|---|---|
| 缺失今日結案 | `defects.closed_at`（`timestamptz`）且 `status='已結案'` | ✓ | ✓ | **可做**；依原球權顯示為監造完成，不宣稱是哪位個人 |
| 查驗今日判定 | `inspections.inspected_at`（`timestamptz`） | **✗**（demo 分支只改 `status`） | ✓ | **補一行 demo 時間戳後可做**；依原球權顯示為監造完成 |
| 送審審定／疑義回覆 | `decided_date`／`answered_date`（`date`） | ✓ | ✓ | **第一版不列**：只有日期，且現行寫法以 UTC `toISOString().slice(0, 10)` 產生，台灣凌晨可能落到前一天 |
| 請款／收款、施工日誌、自主檢查、驗收事件 | `invoice_date`／`paid_date`／`log_date`／`check_date`／`event_date` | ✓ | ✓ | **不列入 `doneToday`**：這些是可回填的業務日期，不等於今天完成操作 |
| 估驗核定、變更核准、疑義結案、觀察處理、試體完成 | 無可靠完成時間 | ✗ | ✗ | **不可做**；不得用 `created_at` 或目前狀態硬湊 |

第一版 `doneToday` 的語意是「登入角色所屬陣營今天完成的可靠狀態轉移」，不是個人績效紀錄。`closed_at`／`inspected_at` 必須轉成 `Asia/Taipei` 日期後再與傳入的固定 `today` 比較；資料不足時寧可不顯示。廠商或機關當天沒有可靠完成事件時，空段是正確結果，不為了畫面有內容加入業務日期。

## 4. 不應列為待辦的項目

| 項目 | 理由 | 建議處置 |
|---|---|---|
| AI 草稿收件匣（`agent_actions` pending） | 硬限制明列「AI 建議本身不得自動成為人工待辦」；且草稿被拒絕不代表任何業務未完成 | 留在 `/agent`，今日待辦最多顯示「Agent 有 N 則草稿待你看」的**非待辦**提示列 |

## 5. Codex 審查後定案

1. **契約義務責任映射採精確白名單**：`廠商 → contractor`、`監造 → supervisor`、`機關 → owner`；`null`、`其他` 與未知文字一律為未指定，不進任何角色的 `mine`。W8-2B 只有廠商責任且廠商能在 `/contract` 操作者列為待辦；監造／機關責任只保留在契約清單，不進「今日待辦」。
2. **W8-2B 只收斂前端**：Dashboard 與 `/alerts` 共用新的前端聚合；不改 `agentTools.ts`、`send-reminders` 或部署 Edge Function。前後端類型集合與未知責任方預設的差異登記為既有限制，若要處理需另行核准，不混入本包。
3. **「今天已完成」只用可靠時間戳**：第一版只收 `closed_at` 與 `inspected_at`，以 `Asia/Taipei` 判斷日期；不混入可回填的業務日期，也不宣稱是某位個人完成。
4. **不建立「今天施工日誌尚未填」待辦**：沒有工地日曆、停工日與開竣工邊界規則前，單看今天有沒有日誌會誤報。W8-0 的畫面是示意，不覆蓋待辦資格五條。
5. **不新增設計單位角色**：依 D-002，`design` 不成為授權、球權或 Agent 角色；設計釋疑仍由監造轉呈，現行 RFI 球權維持監造。
6. **共同可辦的驗收階段不複製資料**：把 `Acceptance.jsx` 現有的階段角色白名單移到 `acceptance.js` 匯出，供驗收頁與待辦聚合共用。竣工確認與複驗同時對監造與機關顯示；任一方完成後，同一階段狀態即退出雙方待辦。這是第二個實際使用點，不另建通用權限層。
7. **「等待對方」只列直接相關項目**：採 §3.2 的角色類型白名單；Dashboard 每段最多 5 筆，完整清單由 `/alerts` 承接，避免首頁再次變長。

複審後補修的兩個日期邊界（原實作有誤，已修正並各補回歸測試）：

- **7 日內門檻被時間分量壓掉一天**：`sampleAlerts`／`acceptanceAlerts`／`computeObligationDue` 都以 `Date` 相減再 `Math.round` 算日差，傳入含時間的「現在」會讓整整 8 個日曆日被算成 7；台北傍晚後開頁時，畫面寫「還有 8 天」的試驗會出現在待辦裡。修正為先把 `today` 正規化成**台北日曆日的午夜**再交給三個引擎，畫面天數與門檻從此是同一個數字。回歸測試對同一台北日曆日的 00:30／12:00／23:30 三個時刻斷言結果一致。
- **每月重複義務讀系統時鐘**：`computeObligationDue` 的 `recurring='monthly'` 分支原本內部呼叫 `new Date()`，使 `buildTodayTasks({ today })` 的固定日期失效。已新增可注入的第三參數 `today`（不傳維持原行為，既有呼叫點不受影響），並在 `contractDue.test.js` 與 `todayTasks.test.js` 各補一條以遠離系統時鐘的日期斷言。

兩條回歸測試都已實際驗證：還原成修正前的寫法會失敗，修正後在 `UTC`／`Asia/Taipei`／`America/Los_Angeles` 三個時區皆通過。

未在本包處理、已登記的後續事項：`demoSeed.js` 沒有 `closed_at`／`inspected_at`，因此 demo 初始狀態的「今天已完成」為空（操作後才出現，已有 E2E 覆蓋）；W8-0 §5.3 的 Agent 手機排序不在 §5～§7 範圍，維持現狀。

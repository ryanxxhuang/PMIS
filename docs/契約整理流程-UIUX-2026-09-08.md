# 契約上傳到三方閱讀：流程與 UI/UX 交付

> 2026-09-08｜本機已完成，未提交／未部署。
> 使用者指定範圍：契約上傳 → AI 自動爬梳 → 重點整理 → 不同角色看不同內容，包含 UI/UX。

本次把既有功能接成連續路徑：使用者先選契約、上傳文件，系統自動分類及整理；結果入口直接打開該契約重點，再依登入角色顯示可見事項。需要查證時可進入同一契約的擷取審核與原文，返回時仍保留原範圍。

## 已完成

| 使用階段 | 行為與介面 |
|---|---|
| 上傳 | 文件與結果頁有一致接續入口；上傳使用真正的 button，可鍵盤操作；避免同頁重複上傳並明示可分析的格式 |
| AI 整理 | 維持自動分類／抽取；進度與錯誤來自既有處理紀錄；缺漏顯示「部分整理」，不冒充完整成功 |
| 查看結果 | 常駐「查看這份契約重點」入口帶入契約範圍；已完成部分可先讀，並提示仍有文件需處理 |
| 整理更新 | 上傳與重試完成後刷新義務；進入結果頁重新載入，仍有 ingestion 處理中時自動刷新 |
| 角色閱讀 | 廠商、監造、機關顯示對應視角說明與責任方事項；一般機關讀者不顯示不可用上傳入口 |
| 查核原文 | 重點與審核／返回連結保留契約範圍；核對疑慮、來源引文與原檔入口延用既有能力 |
| 異常與切換 | 清單查詢分頁；載入失敗顯示重試，不變成無文件；切案後舊回應不覆蓋新畫面 |
| 手機 | 流程入口可換行，文件表改為直向列；檔名、分類、版本、AI 狀態、原因與動作在可見寬度內 |

無可計算到期日的事項改顯示「無到期日」，避免誤導成不需履約。日期算法、核定與完成權限沒有改動。

## 三方範圍

| 登入角色 | 契約內容與履約展示 |
|---|---|
| 施工廠商 `contractor` | 自己可存取的契約與廠商履約事項 |
| 監造單位 `supervisor` | 自己與施工廠商的契約、監造及廠商履約事項 |
| 主辦機關 `owner` | 可存取的三方契約與履約事項 |

沿用 D-018：後端 RLS 決定資料是否能讀取，前端只在已獲授權的資料中選契約與責任方。歷史無契約包資料仍遵循原有相容規則；沒有新增或放寬權限。產品也沒有讓使用者任意選擇另一種登入角色的控制項。

D-019 保留：AI 抽取完成後仍自動確認歸檔，即使帶有核對疑慮；「只看需留意項目」是檢查入口，不是新增的逐條放行要求。人工補登及正式業務核定維持原規則。

## 驗證結果

- 73 個 Vitest 測試檔、820 個測試通過。
- 48 項 Demo E2E 通過，含新增三角色各 1440px／375px 的文件 → 重點 → 文件流程。
- Production build 通過；既有大於 500 kB chunk 警告仍在。
- 新增元件測試覆蓋：上傳結果刷新、契約範圍延續、錯誤重試、部分整理、機關檢視模式、超過 1,000 筆契約分頁、舊案回應遲到、三角色可見事項與處理中空狀態。
- 另外用實際 Contract 元件＋測試資料做桌面／手機靜態渲染目視；修正手機水平表格遮住處理原因的問題，1440px／375px 均無頁面水平溢出，警示位於可見寬度內。此項只驗證版面，互動由元件測試與 E2E 驗證。

以上使用模擬服務與 Demo 資料，沒有對正式契約呼叫 AI，也沒有重新驗證真 Supabase 的上傳／RLS／模型端到端。沒有資料庫 migration，未重跑 pgTAP；不能把介面驗收當成重新證明資料權限或抽取準確率。

## 尚存限制與交付狀態

- 文字型 PDF、DOCX、TXT 可自動分析；圖片、純掃描內容、Excel 與舊版 Word 的內容分析限制仍在。前端已如實提示，沒有新增 OCR。
- 大文件續跑仍由啟動上傳的瀏覽器分頁接力；不能宣稱關閉分頁後保證繼續。頁面會提示保留分頁，既有中斷復原規則不變。
- 24 批上限及真實契約語意品質評測不在本輪 UI/UX 改動內；完整性提示不代表沒有漏抽或語意錯誤。
- 新增契約篩選沿用既有資料，不新增路由、角色或資料表。共用分頁工具沿用目前 1,000 列服務設定，未做大型案件效能壓測。
- 工作區保留上一批的 Edge 完整性修正；正式上線需要發布前端與該 Edge Function。此次沒有 commit、push、部署或修改正式資料。

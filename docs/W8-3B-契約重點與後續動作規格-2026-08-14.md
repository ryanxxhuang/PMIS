> 狀態：**DELIVERED — PR #15 已合併部署（2026-08-15）**；F1～F4 依 §11 完成；真案三角色桌面／375px 實機目視待補（無可用帳號，列 W8-5 前收尾）
> 日期：2026-08-14  
> 依據：W8-0 已核准報告、D-003、D-012、D-015

## 1. 五行實作契約

- **問題**：`/requirements` 把原始擷取、六個篩選、逐筆審查與契約重點擠在同一頁，使用者被誤導成必須逐筆清空 AI 建議。
- **目標**：一般進入時先看「已生效的契約重點」與最多 6 筆「值得留意的整理結果」；需要時才展開完整追溯與專業審查。
- **不做**：不新增路由、資料表、migration、Edge Function、角色、批次核定、模糊去重或未存在的送審／查驗建立器。
- **影響**：最小修改 `Requirements.jsx`、既有 `requirementReview.js` 與相關測試；並同步導覽與專案文件的入口命名。
- **驗收**：一般畫面無「待審清空」壓力；期限捷徑必須真正呼叫現有 RPC 並建立期限追蹤；其他類型不假裝已能建立工作流；原始列、來源、歷史 run 與原審查權限仍可完整追溯。

## 2. 現有能力盤點

| 現有資料／動作 | 能安全呈現的事 | 本包邊界 |
|---|---|---|
| `requirements` | 標題、類型、責任方、履約階段、觸發／週期規則、允收標準、應留存證、狀態 | 可組成契約重點；不自行推測罰則、金額或實際到期日 |
| `requirement_sources` | 文件、版本、頁碼、節次、條款、原文與來源是否已核對 | 簡表上只顯示來源摘要；完整原文放在展開詳情 |
| `review_requirement` RPC | 監造／機關可核定、駁回、廢止；伺服器記錄人員與時間 | 仍是唯一契約決定入口；不寫第二套狀態更新 |
| D-012 期限單向物化 | 核定 `deadline` 時會同事務、可重複地建立／更新 `contract_obligations` | 只有這類能稱為「核定並加入期限追蹤」 |
| `requirement_work_items` | 對應真實 BOQ 工項的 AI 建議與人工核可 | 保留在詳情，不當一般使用者的首要動作 |
| `requirement_artifact_links` | 顯示已核定 Requirement 已連到哪個真實流程項目 | 目前只讀；沒有送審、查驗、試驗或檢查表的建立精靈 |
| `contract_obligations.penalty` | 舊期限 runtime 可能已有罰則 | 新 Requirement 沒有 penalty 欄位，本包不顯示「罰則 N 筆」假精準統計 |

### 2.1 資料範圍

1. **已生效**：所有 `status = approved` 的 Requirement，不受「最新 run」限制；已核定的契約事實不能因重新擷取而消失。
2. **值得留意**：`draft_ai` 或 `needs_review`；人工／轉入資料保留，AI 只取每個文件版本最新成功 run。
3. **追溯資料**：所有狀態與歷史 run，含 `rejected` 與 `superseded`；不刪除、不隱藏史料。
4. 現行 300 筆有界查詢維持不變；畫面不宣稱是全庫精確總數。

## 3. 定案畫面

### 3.1 一般模式（預設）

`PageHeader` 改為：

- 標題：**契約重點**
- 說明：**先看已生效與值得留意的內容；原始 AI 擷取結果仍可完整追溯。**

不放六個篩選，也不在頁首顯示「待人工確認 106 筆」。順序只有三區：

1. **已生效的契約重點**
   - 使用簡潔列，預設最多 6 筆。
   - 每筆顯示：類型、標題、責任方、可讀規則、來源狀態。
   - 期限類可「前往期限追蹤」到 `/contract`；其他類只「查看內容與來源」。
   - 其餘內容以「查看更多契約重點」在本頁展開，不新增路由。
2. **值得留意的整理結果**
   - 最多 6 筆，不把全部 AI 建議當成待辦。
   - 穩定排序：期限 → 送審 → 查驗／試驗 → 檢查表 → 佐證／照片／報告 → 其他；同類以已核對來源優先，再用建立時間與 id 穩定排序。
   - 不顯示 AI confidence 當成權威或優先級。
   - 區塊底部只用中性文案：「其餘擷取結果已保留在追溯區，不必逐筆清空。」
3. **查看全部擷取結果**
   - 一個明確開關，點開後才顯示現行六個篩選、完整列表、歷史 run 與審查詳情。
   - 加上「這是追溯與專業審查資料，不是必須清空的待辦清單」。
   - 現有的篩選、編輯、核定、駁回、廢止、BOQ 工項連結與已連結流程項目全部保留。

### 3.2 單筆展開

一般模式的「查看內容與來源」與追溯模式的列表選取，共用現有詳情卡，不再寫第二份詳情 UI。它保留：

- Requirement 內容、允收標準與應留存證。
- 完整文件／版本／頁碼／節次／條款／引文。
- 只對監造／機關顯示的編輯與契約決定。
- BOQ 工項連結與已有 artifact 連結。

## 4. 後續動作的真實邊界

| 項目 | 廠商看到 | 監造／機關看到 | 實際寫入 |
|---|---|---|---|
| 已核定期限 | 前往期限追蹤 | 前往期限追蹤 | 無，只導航 `/contract` |
| 未核定期限，規則完整，且 AI 來源已核對（或為人工／轉入） | 「待監造／機關決定」 | 「核定並加入期限追蹤」 | `review_requirement('approve')`；D-012 同事務物化 obligation，成功後 `reloadObligations()` |
| 未核定期限，規則不完整或 AI 來源尚未核對 | 「查看內容與來源」 | 「查看並補齊期限」，進入現有詳情，不直接核定 | 只有使用者在詳情明確儲存／核定時才寫入 |
| 未核定送審、查驗、試驗、檢查表、佐證等 | 查看內容與來源 | 查看內容與來源；詳情仍可用現有「核定為契約規則」 | 核定只改 Requirement 權威狀態，不建立送審／查驗等活躍流程 |

所有捷徑核定都必須保留現有確認視窗、伺服器權限與伺服器回傳後才更新 UI；不做 optimistic approval。

## 5. 去重與排序

1. 去重只影響預設畫面，不更新、拒絕或刪除任何 Requirement。
2. 只合併「狀態家族、類型、責任方、階段、標題、描述、觸發／週期設定、允收標準、應留存證」全部相同的內容；只對空白與空格正規化，不做模糊／語意合併。
3. 已核定與未核定不直接混成同一組；若完全相同的內容已有核定版，預設建議區不再重複顯示未核定版，但追溯區仍看得到。
4. 被合併的卡片顯示「同內容 N 筆擷取」，展開時可看全部引註；快速核定只作用於當前代表列，不假裝批次更改其他列。

## 6. 錯誤、空狀態與手機

- Requirement、run、source 或 version 任一必要查詢失敗，顯示「契約重點載入失敗」與重試；不把失敗假裝成 0 筆。
- AI 已完成但 0 筆，沿用 W8-3A 語意：「沒有找到契約重點建議，不需處理」。
- 沒有 completed run 時才導回 `/contract` 查看文件處理狀態。
- 375px 時卡片欄位改直排，按鈕全寬；不允許文件級水平滾動。

## 7. 最小實作清單

### 7.1 Codex 處理（複雜／高風險）

1. 在既有 `requirementReview.js` 增加「預設契約重點範圍、精確去重、穩定排序、捷徑動作資格」純函式；不新建通用框架。
2. `Requirements.jsx` 分成預設摘要與可展開的現有追溯區，共用同一份 detail/review 狀態與 RPC。
3. 期限捷徑沿用 `review_requirement`，釘住只有授權角色、符合來源／規則條件時才出現。
4. 補單元、頁面回歸、完整 Vitest、Demo E2E 與 build；本包不動 DB，不新增 pgTAP 或真後端 E2E。

### 7.2 Opus 處理（簡單／低風險，待核心穩定後）

1. 依 Codex 已完成的 DOM 與文案做小幅間距、換行與 375px 排版磨光；不改資料範圍或動作條件。
2. 更新受文案影響的 Demo E2E locator，不新增流程。
3. 提供三角色桌面／375px 目視回報；不單獨 commit、push 或部署。

## 8. 最低測試

1. 舊 run 的 approved Requirement 仍在預設契約重點；舊 run 的未核定 AI 列只在追溯區。
2. rejected/superseded 不進預設摘要，但完整擷取結果仍可找到。
3. 精確重複合併；只要責任方、階段、規則或內容任一不同就不得合併；原始列數不變。
4. 建議區最多 6 筆且排序穩定；不顯示「待審 N 筆」或清空引導。
5. contractor 無核定／駁回／supersede 控制；owner/supervisor 維持伺服器權限。
6. 只有「規則完整，且 AI 來源已核對（或人工／轉入）」的 deadline 顯示快速動作；核定後服務器回傳 approved 且呼叫 `reloadObligations()`。
7. 送審、查驗、試驗、檢查表、佐證等不顯示「建立流程」之類尚未存在的按鈕。
8. 查詢失敗有錯誤與重試，不顯示假空狀態。
9. 完整 Vitest、Demo E2E、production build 全綠；三角色實案畫面與 375px 無水平溢出。

## 9. 明確不在 W8-3B

- 批次核定／駁回、自動清空 AI 建議、LLM 語意去重。
- 建立送審、ITP、檢查表、試驗或佐證的 wizard／generator。
- 由 AI 自動核定契約規則，或讓未核定建議進入今日待辦／Agent 工具。
- 新增 penalty 欄位、罰則解析或沒有資料來源的統計。
- 修改三方角色、RLS、Requirement 權威邊界或 Contract runtime。

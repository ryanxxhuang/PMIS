## 0. 結論摘要(先看這頁)

**新定位一句話**:
> **每個工程人各配一個懂本案契約的 AI Agent;人只做判斷與簽核,打字的事交給 agent。**

四個角色 = 台灣三級品管 + 現場生產,一一對應:

| Agent | 使用者 | 在三級品管的位置 | 一句話價值 |
|---|---|---|---|
| **現場 Agent** | 廠商工地主任/現場工程師 | 生產端 | 拍照上傳→日誌自動寫完→數量自動流進估驗 |
| **品管 Agent** | 廠商品管人員 | **一級**(自主檢查) | 查驗照片上傳→自主檢查表填完、不合格自動開缺失 |
| **監造 Agent** | 監造/專案管理廠商 | **二級**(品保查證) | 送審、查驗、估驗的審查要點與意見草稿,ITP 到點自動叫人 |
| **機關 Agent** | 主辦機關承辦/監工 | **三級**(查核) | 期程/罰則/付款法定期限儀表 + 勾稽鏈防弊稽核 |

**這次改版的技術核心只有三件事**(其餘都是既有資產的重新包裝):

1. **Agent Runtime**:把現在 14 個「一次性抽取器」升級成**多輪 tool-use 迴圈**,agent 能自己查資料、自己填草稿。
2. **動作工具白名單**:agent 只能呼叫「查詢」與「產生草稿」工具,**核定/判定/結案/凍結一律沒有工具可用**——狀態轉移永遠走既有 8 個 DB trigger + 人簽核。這是產品的法遵護城河,不可讓 AI 碰。
3. **佐證鏈(evidence graph)**:估驗明細 ↔ 施工日誌 ↔ 查驗單 ↔ 試體 ↔ 照片互相掛勾,畫面上一欄「佐證」點得進去,列印時自動夾附。

**產品因此可以變簡單**:側欄 22 項 → **6 個面**(1 個 Agent 主控台 + 5 個資料面),其餘 20 個路由降為分頁/下鑽(路由全保留,深連結不壞)。

**成本**:以 Sonnet 5 跑 agent 迴圈 + prompt caching,**每案每月約 US$30(≈ NT$1,000)**,詳見 §10。

**網域**:實測 190+ 個 `.ai` 候選(whois.nic.ai 直查)。可註冊首選 **`conpm.ai`**、**`sitesquad.ai`**、**`constructagent.ai`**,完整清單見 §12。

## 1. 現況盤點:你已經有什麼(這次改版的地基)

盤點結果——**地基比你以為的更完整,缺的只有「agent 化」那一層**。

| 面向 | 現況 | 改版時的角色 |
|---|---|---|
| 資料脊椎 | PCCES 標單 → `work_items` 樹(3,000+ 項) | **不動**,agent 的世界觀來源 |
| 角色與權限 | `profiles.org_type` ∈ {contractor, supervisor, owner};RLS 分角色 + 8 個狀態轉移 trigger;18 項權限矩陣實測過 | **不動**,直接變成 agent 的權限模型(見 §5) |
| 量體流 | `daily_log_items(work_item_id, qty_today)` → `fillValuationFromSiteLogs()` → `valuation_items.source='daily_log'` | **已經做完你 #3 的一半**,缺的是佐證連結與列印夾附 |
| 三級品管 | 自主檢查表(範本→實測→自動判定→開缺失→公定式列印)、ITP W/H/R、取樣試驗齡期、統一缺失引擎、機關風險稽核 `/audit` | **已經很完整**,agent 只是換一個入口 |
| AI 能力 | 14 個 Edge Function:視覺辨識(白板/缺失/工安/施工照)、文件抽取(契約/送審/需求)、草稿生成(月報/RFI/估驗說明/稽核意見)、天氣、每日提醒信 | **變成 agent 的工具箱**,不是重寫 |
| Copilot | `/assistant` + 右下角浮動鈕;前端組 `buildAssistantFacts()` 事實快照 → `assistant-chat` 回答 + 出處 | **原型正確、但唯讀**,是這次要升級的對象 |
| 確定性引擎 | `boqCalc / changeOrders / contractDue / qc / itp / penaltyCalc / integrityAudit / ballInCourt` + 417 個 pgTAP / vitest | **不動**,AI 永遠不准自己算數字 |

### 現況的三個缺口(這次要補的)

| 缺口 | 現在的樣子 | 改版後 |
|---|---|---|
| **AI 不會動手** | `claudeJson()` 強制 `tool_choice` 單一工具、單輪、回一包 JSON;前端拿到再自己寫入 DB | agent 多輪迴圈,自己查、自己開草稿、自己掛佐證 |
| **AI 不會跨模組串** | copilot 只能「看」事實快照,不能「做」;每個功能各自一個按鈕,使用者要知道去哪按 | 使用者只描述目的(「今天查驗的照片都上傳了,幫我把查驗單做掉」),agent 決定用哪些工具 |
| **佐證是斷的** | 估驗數量來自日誌,但畫面上看不到「這 1,000 m³ 是哪幾天的日誌」;列印不夾附;`obligation_evidence` 只做了「義務↔送審」一條線 | 統一 `evidence_links` 表,六條線全通,畫面一欄 + 列印自動夾附 |

## 2. 核心主張:四個 Agent + 一層共享事實

```
                    ┌──────────────────────────────────────────┐
                    │  專案共享事實層(單一真相)                │
                    │  契約/標單/日誌/查驗/估驗/送審/變更/佐證   │
                    │  ── Supabase + RLS(誰能看什麼,已上線)   │
                    └───────────────┬──────────────────────────┘
                                    │  同一份資料,四種視角
        ┌──────────────┬────────────┼────────────┬──────────────┐
        │              │            │            │              │
   ┌────▼────┐   ┌─────▼────┐  ┌────▼─────┐ ┌────▼─────┐
   │ 現場    │   │ 品管     │  │ 監造     │ │ 機關     │
   │ Agent   │   │ Agent    │  │ Agent    │ │ Agent    │
   └────┬────┘   └─────┬────┘  └────┬─────┘ └────┬─────┘
        │              │            │            │
        └──────── 交接的是「單據 + 球」,不是聊天 ────────┘
                 (ball-in-court 事件流,見 §6)
```

**三條設計紅線**(違反就會毀掉產品的可信度,請寫進 CLAUDE.md):

1. **AI 只產生「草稿」**。所有 agent 寫入的資料一律 `status='草稿' / 'draft_ai'`,且必經人在畫面上覆核送出。核定、判定、結案、驗收、凍結——**agent 的工具箱裡根本不存在這些工具**(不是靠 prompt 約束,是靠工具白名單)。
2. **數字永遠由確定性引擎算**。agent 可以說「本期估驗 1,234,567 元」,但這個數字必須是 `boqCalc.js` 算出來、由工具回傳的;agent 不准自己乘除。現有 `assistant-chat` 的反幻覺紀律(只准引用快照值)延伸成工具層的硬約束。
3. **每個 agent 動作都留痕**。新增 `agent_actions` 表記錄每一筆草稿/建議(角色、種類、目標、理由、佐證、人覆核結果)。這同時是:機關要的稽核軌跡、你調 prompt 的訓練資料、以及「AI 建議採納率」這個能對外講的指標。

## 3. 四個 Agent 的定義(職責 × 工具 × 主動行為)

### 3.1 現場 Agent(廠商工地主任 / 現場工程師)

| 項目 | 內容 |
|---|---|
| **痛點** | 每天收工後花 40 分鐘補日誌;數量憑印象;照片一堆沒歸位 |
| **主動行為** | 每日 17:00 推「今天的日誌我先擬好了」——吃昨日日誌 + 今日照片 + 天氣 API + 排程工項 |
| **主力工具** | `draft_daily_log`(照片批次 → 工項/數量/說明)、`classify_photos`(既有 `classify-site-photo`)、`read_whiteboard`、`fetch_weather`、`search_boq`(模糊比對工項)、`raise_to(品管)` |
| **輸出** | 施工日誌草稿(含公定格式全欄位)+ 照片自動歸工項 + 明日缺料/缺工提醒 |
| **下游效果** | 日誌數量 → `daily_log_items` → 估驗自動累計(既有 `fillValuationFromSiteLogs`) |

### 3.2 品管 Agent(廠商品管人員 — 一級品管)

| 項目 | 內容 |
|---|---|
| **痛點** | 自主檢查表照著範本一格一格填;試體齡期靠記;缺失追蹤靠 LINE |
| **主動行為** | 「今天有 3 個工項達查驗時機、2 組試體 7 天齡期到期、1 件缺失明天逾期」 |
| **主力工具** | `draft_inspection`(**你的 #4:查驗照片批次上傳 → 依範本量化標準填實測值 → 自動判定**)、`draft_defect`、`list_pending_samples`(既有 `qc.js`)、`check_submittal_readiness`、`raise_to(監造)` |
| **輸出** | 自主檢查表草稿(公定式可列印)、不合格自動帶出缺失草稿、送審備齊清單 |
| **紅線** | 判定合格/不合格用 `qc.js` 的量化標準比對(確定性),AI 只負責從照片讀出實測值並標「需人工確認」 |

### 3.3 監造 Agent(監造 / 專案管理廠商 — 二級品管)

| 項目 | 內容 |
|---|---|
| **痛點** | 送審審查是最大時間殺手;估驗審核要翻日誌對數量;ITP 到點沒人通知 |
| **主動行為** | 「廠商送了 2 件送審(其中 1 件是再送)、1 期估驗待審、明天有 1 個 H 點必須到場」 |
| **主力工具** | `review_submittal` / `read_submittal`(既有,逐項比對契約需求)、`cross_check_valuation`(**估驗對日誌:本期報 1,000 m³,日誌加總 985 m³ → 差異 15 m³ 需說明**)、`draft_rfi_reply`、`draft_supervisor_report`、`itp_due`、`raise_to(廠商/機關)` |
| **輸出** | 審查要點 + 意見草稿 + **建議**判定(核定仍是人按) |
| **紅線** | 規範依據只可引用「本案已解析的履約需求」;通用要點須標「通用」;絕不捏造條號 |

### 3.4 機關 Agent(主辦機關承辦 / 監工 — 三級品管)

| 項目 | 內容 |
|---|---|
| **痛點** | 手上 5 個案子,只想知道「哪個要出事」;付款法定期限逾期要被追;怕被審計挑 |
| **主動行為** | 跨案早報:「A 案進度落後 8%、逾期罰款試算 42 萬;B 案估驗核定後第 13 天未付款(法定 15 天)」 |
| **主力工具** | `portfolio_status`(跨案)、`contract_deadlines`(既有 `contractDue` + `penaltyCalc`,**確定性 regex 抽罰率**)、`integrity_audit`(既有 6 項確定性勾稽 + `audit-summary` 寫意見)、`acceptance_deadlines`(驗收法定期限) |
| **輸出** | 期程/罰則儀表、逾期預警、勾稽鏈異常提示(**「值得複查的異常」,非違規認定**) |
| **紅線** | 機關端 RLS 唯讀,`cost_items`(廠商毛利)連讀都禁——agent 用使用者 JWT,自動繼承這個限制 |

### 3.5 角色模型怎麼加「品管」?(重要:不要動 org_type)

`org_type` 三值(contractor / supervisor / owner)是 RLS + 8 個 trigger + 18 項權限矩陣的地基,**動它等於重測全部安全性**。品管人員在編制上屬於廠商,權限就是 contractor。

**做法**:`project_members` 加一欄 `job_role`,**只驅動 agent persona 與「待我處理」排序,完全不參與權限判斷**。

```sql
alter table public.project_members
  add column if not exists job_role text
  check (job_role in ('field','qc','supervisor','owner','pm'));
-- 權限仍舊全部看 profiles.org_type;job_role 只決定「你配到哪個 agent」
```

一行 migration,零安全性風險,四個 persona 就位。

## 4. 你點名的五件事,怎麼落地

### #3 估驗自動化 + 佐證夾附

現況:`daily_log_items` → `fillValuationFromSiteLogs()` → `valuation_items(source='daily_log')` **已經在跑**。缺的是「看得到、印得出」的佐證。

**要補的**:

```sql
-- 通用佐證圖(取代散落的單點外鍵,含既有 obligation_evidence)
create table public.evidence_links (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.projects(id) on delete cascade,
  from_type text not null,   -- valuation_item | obligation | defect | acceptance ...
  from_id   uuid not null,
  to_type   text not null,   -- daily_log | inspection | test_sample | photo | submittal
  to_id     uuid not null,
  relation  text not null default 'evidence',
  created_by uuid references auth.users(id),
  created_at timestamptz not null default now(),
  unique (from_type, from_id, to_type, to_id)
);
```

- **自動掛勾**:`fillValuationFromSiteLogs` 在寫 `valuation_items` 時,同步寫入「這個工項的累計數量,是由這幾筆 `daily_log` 貢獻的」——**確定性,不用 AI**。
- **畫面**:`/valuation` 明細表加一欄「佐證」,顯示 `📄 12 筆日誌 · 3 張查驗單 · 2 組試體 · 18 張照片`,點進去展開。
- **列印**:`/valuation/package` 現有「本期明細 + AI 施工說明 + 照片」再加一段——**按工項自動夾附貢獻該數量的施工日誌(公定格式)**。這就是你說的「估混凝土 1000 立方,紙本後面自動附日誌」。
- **監造端加值**:`cross_check_valuation` 工具做「估驗報量 vs 日誌加總」差異表,監造 agent 主動指出不符——這是監造最想要、機關最買單的功能。

### #4 查驗照片批次上傳 → 查驗單自動填完

現況:`describe-defect` 一張照片 → 缺失欄位;`qc.js` 有自主檢查表範本(量化標準 → 實測值 → 自動判定)。

**要補的**:`draft_inspection` 工具 = 批次照片 → 視覺讀「檢查項目 + 實測值 + 位置」→ **對範本的量化標準跑確定性判定** → 產生檢查表草稿;任何不合格自動帶出缺失草稿(既有統一缺失引擎)。AI 讀不準的值標 `needs_review`,畫面上黃底,人補一格就送出。

### #5 工安缺失照片 → 自動找對表單填好

現況:`analyze-safety-photo` 已做「危害類別 + 違反法規依據 + 嚴重度 + 改善建議」,`/safety` 有工安四類紀錄。

**要補的**:agent 多一步「選表」——照片判讀結果 → 決定該開哪一類工安紀錄(缺失改善 / 教育訓練 / 自動檢查 / 通報)→ 填該類表單草稿 → 掛佐證照片 → `raise_to(監造)`。使用者的動作從「開表→選類→填欄位→附照片」變成「丟照片→覆核→送出」。

### #1/#2 契約時程 Dashboard、進度曲線

現況:`/contract`(AI 解析契約義務+罰則)、`/alerts`、`/progress` S 曲線、`penaltyCalc` 全都在。

**要補的不是功能,是「一頁看完」**:把契約期程、S 曲線、金流、逾期罰款試算收進 `/dashboard` 一頁(角色化:機關看罰則與付款期限、廠商看進度與請款、監造看待審與到期查驗)。這是收斂,不是開發。

## 5. 技術架構:Agent Runtime 怎麼做

### 5.1 新增 `_shared/agent.ts`(工具迴圈)

現有 `claudeJson()` 是單輪強制單工具。新增並存的 `claudeAgent()`:

```ts
// supabase/functions/_shared/agent.ts
export async function claudeAgent(opts: {
  model: string            // 預設 MODELS.agent = 'claude-sonnet-5'
  system: string           // persona + 紅線
  tools: ToolDef[]         // 該角色的工具白名單
  messages: Message[]
  maxSteps?: number        // 預設 8,防跑飛
  exec: (name: string, input: unknown) => Promise<unknown>  // 工具執行器
}): Promise<{ text: string; actions: AgentAction[]; steps: number }>
```

迴圈:呼叫 Messages API(帶 `tools`,**不強制 `tool_choice`**)→ `stop_reason === 'tool_use'` 就執行工具、把 `tool_result` 接回 → 直到 `end_turn` 或 `maxSteps`。

**參數建議**(依 Claude API 現況):
- `model: 'claude-sonnet-5'`(agent 迴圈主力)、`output_config: { effort: 'high' }`
- 視覺批次辨識維持 `claude-haiku-4-5`;監造審查/機關稽核這種「判斷成本高」的用 `claude-opus-5`
- **不要**傳 `temperature/top_p/top_k`、**不要**傳 `budget_tokens`——Sonnet 5 / Opus 5 會 400
- 思考:Sonnet 5 省略 `thinking` 即為 adaptive;`max_tokens` 要留餘裕(思考+輸出共用額度)
- **Prompt caching**:`tools` + `system` + 專案事實快照放前段並下 `cache_control`,使用者問題放最後。這是成本的關鍵(見 §10)

### 5.2 權限:agent 的權限 = 使用者的權限(零額外程式碼)

Edge Function 用**呼叫者的 JWT** 建 Supabase client:

```ts
const supabase = createClient(URL, ANON_KEY, {
  global: { headers: { Authorization: req.headers.get('Authorization')! } },
})
```

→ 所有工具查詢/寫入自動走 RLS。機關的 agent 讀不到 `cost_items`、監造的 agent 碰不到請款、廠商的 agent 改不了已核定估驗——**全部是既有 RLS 與 8 個 trigger 擋的,一行新權限程式碼都不用寫**。這是這次架構最漂亮的地方,也是安全性能通過機關檢視的理由。

### 5.3 工具白名單(依角色分發)

| 類別 | 工具(所有角色共用) |
|---|---|
| 查詢 | `get_project_facts(modules[])`、`search_boq(keyword)`、`list_daily_logs(range)`、`get_requirements(topic)`、`get_valuation(period)`、`list_my_open_items()`、`find_evidence(work_item, range)` |

| 角色 | 草稿工具(全部只寫 `status='草稿'`) |
|---|---|
| 現場 | `draft_daily_log`、`classify_photos`、`attach_evidence` |
| 品管 | `draft_inspection`、`draft_defect`、`attach_evidence` |
| 監造 | `draft_submittal_review`、`draft_rfi_reply`、`cross_check_valuation`、`draft_supervisor_report` |
| 機關 | `run_integrity_audit`、`draft_audit_note`、`penalty_estimate` |
| 全部 | `raise_to(role, item, note)` — 交接 |

**永遠不存在的工具**:`approve` / `certify` / `close` / `accept` / `delete` / `update_approved_*`。

### 5.4 稽核軌跡

```sql
create table public.agent_actions (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.projects(id) on delete cascade,
  actor_user uuid not null references auth.users(id),
  agent_role text not null,          -- field | qc | supervisor | owner
  kind       text not null,          -- draft_daily_log | draft_inspection | ...
  target_table text, target_id uuid,
  rationale  text,                   -- agent 為什麼這樣填
  evidence   jsonb,                  -- 引用了哪些資料
  status     text not null default 'pending',  -- pending | accepted | edited | rejected
  created_at timestamptz not null default now()

```

## 6. 跨角色協作:agent 不聊天,交接的是「單據 + 球」

你的 #2。**不要做 agent 互相對話**——不可控、不可稽核、成本爆。正確模型是既有的 ball-in-court 事件流:

```
現場 Agent 產生日誌草稿 → 人送出
   └→ 品管 Agent 看到「有新日誌,其中 3 個工項達查驗時機」→ 主動擬查驗單
        └→ 人送出查驗 → 球給監造
             └→ 監造 Agent 主動擬審查意見 + 對照日誌數量
                  └→ 監造核定 → 球給廠商請款 / 給機關備查
                       └→ 機關 Agent 主動跑勾稽鏈,異常才出聲
```

實作:`ballInCourt.js` 已有推導邏輯,把它變成**每個 agent 的「今日待我處理」來源**,再加 `raise_to` 工具讓 agent 明確把球丟出去並附草稿。使用者體感是「東西自己流過來,而且已經填好一半」——這就是你要的跨角色協作。

## 10. 成本與模型策略

**現況模型分工**(`_shared/claude.ts`)要擴成三層:

| 用途 | 模型 | 單價(每 M tokens) |
|---|---|---|
| 視覺批次(照片辨識、白板、缺失) | `claude-haiku-4-5` | $1 / $5 |
| **Agent 迴圈主力**(現場/品管/機關) | `claude-sonnet-5` | $3 / $15(2026-08-31 前優惠 $2 / $10) |
| 高判斷成本(監造審查、契約解析、勾稽稽核意見) | `claude-opus-5` | $5 / $25 |

**每案每月估算**(4 角色 × 每人每日 8 輪 × 30 天 ≈ 960 輪):

| 項目 | 量 | 成本 |
|---|---|---|
| 輸入(每輪約 12k,80% 命中快取) | 9.2M 快取讀 + 2.3M 未快取 | $2.8 + $6.9 |
| 輸出(每輪約 1.5k) | 1.44M | $21.6 |
| 視覺(每日 100 張照片) | ~4.8M | $4.8 |
| **合計** | | **≈ US$36 / 月 / 專案(≈ NT$1,150)** |

**降本的關鍵是 prompt caching,不是換小模型**:
- `tools` → `system` → 專案事實快照 這段必須**逐位元組穩定**(不可塞 `new Date()`、不可讓工具清單依人變動、JSON 要排序輸出),`cache_control` 下在事實快照末端,使用者問題放它後面。
- 快取讀約為輸入價的 0.1×;做對這件事,輸入成本掉到 1/3。
- Sonnet 5 最低可快取前綴 1024 tokens,事實快照本來就超過,天然適合。
- 用 `usage.cache_read_input_tokens` 監控;若長期為 0,就是有東西在偷偷讓前綴變動。

**定價含意**:每案 AI 成本 NT$1,150/月。若對機關以「每案每月」訂閱,毛利安全區大約要 NT$4,000 以上;對廠商則可用「每案 AI 額度」制。

## 11. 風險與對策

| 風險 | 對策 |
|---|---|
| **AI 填錯數量進了估驗** | 數量欄位一律標來源(日誌/照片/人工),agent 不得憑空產生數量;`cross_check_valuation` 讓監造端自動抓差異;已核定資料 trigger 凍結 |
| **agent 越權** | 工具白名單(核定類工具不存在)+ 使用者 JWT 走 RLS + 8 個 trigger。三層防護,任一層失效仍擋得住 |
| **AI 捏造法規條號** | 沿用既有紀律:只准引用本案已解析的履約需求;通用要點須標「通用」;`analyze-safety-photo` 的 grounded 模式延伸到所有審查工具 |
| **成本失控** | `maxSteps` 上限 8;每案每月 token 上限;prompt caching;視覺一律 Haiku |
| **使用者不信任、退回手填** | 草稿收件匣顯示「AI 填了 12 欄、你改了 2 欄」;`agent_actions` 統計採納率,對外是賣點、對內是調 prompt 的依據 |
| **改版打壞既有 417 測試** | 新架構「加法」為主(新表、新 function),不改既有 RLS/trigger/引擎;每批部署前跑全套 |

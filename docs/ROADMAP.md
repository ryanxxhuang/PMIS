## 目前階段：文件基準

目標是讓現況、已定案決策、候選改動與歷史證據分開。完成條件：

- 新工作能從 `CURRENT.md` 找到現況。
- 已確認原則都能從 `DECISIONS.md` 找到。
- 每份架構文件都有清楚狀態。
- 歷史報告不再被誤認為現行規格。
- 後續開發遵守 `DEVELOPMENT.md`。

## 下一批候選，只先討論一項

### C-001｜釐清 Requirement 與期限追蹤的責任

- **狀態**：CANDIDATE，尚未定案。
- **現況**：`requirements` 負責可審查的契約要求；`contract_obligations` 負責現有期限與提醒流程，migration 仍會建立相容鏡像。
- **要先回答**：兩者要保持同步、改成單向產生，還是完全解耦？舊資料怎麼保留？
- **這一階段不做**：不改 trigger、不刪欄位、不清資料、不改 UI。

### C-002｜收斂兩套成員模型的命名

- **狀態**：CANDIDATE。
- **現況**：`project_members` 管存取與 admin；`project_parties`／`project_memberships` 管契約方與身分快照，但名稱仍容易誤用。
- **要先回答**：是否只補命名與 helper，或真的需要移除相容模型？

### C-003｜降低雙引擎人工同步

- **狀態**：CANDIDATE。
- **現況**：Demo 前端判定與正式 DB／Edge 判定有人工同步點。
- **要先回答**：哪些 demo 行為仍有商業價值，哪些可以直接共用純函式或移除？

## 執行規則

1. 一次只選一個候選。
2. 先補五行規格與驗收條件。
3. 使用者把狀態改為 `APPROVED FOR IMPLEMENTATION` 後才寫程式。
4. 完成後更新 `CURRENT.md`，再處理下一項。

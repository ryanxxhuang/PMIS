# W8-5 三角色真實使用者驗收清單

> 狀態：**桌機輪已執行並回填（2026-08-19，單人自測）；手機輪未執行（使用者暫緩）**

## 一、目的

W8-5 的完成定義不是「工程師覺得畫面沒壞」，而是：

> **三個角色的真實使用者（廠商、監造、機關），在沒有人在旁邊解釋的情況下，
> 每一步都知道「下一步該做什麼」，並且真的把任務做完。**

因此每一步的通過條件都有兩個獨立的欄位：

| 欄位 | 意義 |
|---|---|
| **知道下一步** | 測試者不必問人、不必猜，看畫面就知道接下來要做什麼 |
| **完成任務** | 測試者實際把該步驟做完（資料真的存進去／狀態真的轉移） |

兩者可以分離：「做完了但一路在問」是**未通過**，因為那代表產品在靠人解釋撐著。

## 二、環境與準備

- **站台**：正式站（不是本機 dev）。測試資料一律用測試專案，不要動真案。
- **裝置**：每個角色**跑兩輪**——
  1. **手機實機**（寬度 375px 級距，例如 iPhone SE／13 mini；用瀏覽器縮放模擬不算數，觸控目標要用真手指驗）
  2. **桌機**（1440px 以上）
- **帳號**：三個角色各一組已加入同一測試專案的帳號（廠商／監造／機關）。
- **旁觀者規則**：陪測的人**全程不主動說話**。測試者開口問，就記一筆「知道下一步 = 否」，然後才回答。
- **記錄方式**：每一步記三件事——① 知道下一步（是／否）② 完成任務（是／否）③ 卡住的原句（測試者說了什麼、看了哪裡）。
  第三欄最有價值，改版靠它，不要只打勾。

### 二之一、前置準備（非測試、任何人可協助，約 30 分）

腳本假設專案裡已存在可操作的資料；下列種子沒種好，多個步驟會原地卡死。

1. 三個測試帳號註冊並確認信箱：廠商／監造／機關各一（註冊時選對身分）。
2. 用**廠商帳號**建測試專案 → 「專案文件」上傳標單 XML（有契約檔一併上傳）→ 「三方成員」邀請監造與機關帳號（邀請時指定身分）。
3. **開啟正式模式**（成員頁，需輸入專案名確認）。不開的話建立者保有跨角色權限，廠商測試者會看到核定按鈕，測不出三方分權。開了不能關，但測試專案用完可整案刪除。
4. 種資料（都用廠商帳號做）：
   - 施工日誌：日期選**昨天**，填 1–2 個工項數量後存檔——給 C-4「複製昨日」用。
   - 品質查驗：提出查驗申請 ×2——給 S-2／S-3 判定用。
   - 變更設計：新增 1 筆變更＋1–2 條明細——給 O-3／O-4 核定用。
   - 驗收結算：登錄「報竣」——給 O-7／O-8 竣工確認用。
5. 要跑桌機第二輪的話，**再準備一個同樣種好資料的測試專案**——第一輪會把狀態消耗掉（估驗核定完就不能再核一次）。

### 二之二、執行順序（交錯跑，不要照角色一次跑完）

腳本之間有依賴：缺失要等監造判不合格才產生、複查要等廠商提送、變更核定與竣工確認要等前置種子。照下列順序跑就不會卡住：

| 輪 | 角色 | 步驟 | 說明 |
|---|---|---|---|
| 1 | 廠商 | C-1～C-6、C-9～C-11 | 跳過 C-7／C-8（缺失還不存在） |
| 2 | 監造 | S-1～S-3 | S-3 判不合格會自動開出缺失 |
| 3 | 廠商 | C-7～C-8 | 處理剛開出的缺失、提送複查 |
| 4 | 監造 | S-4～S-8 | 複查結案 → 核定估驗 → 送審 → 唯讀日誌 |
| 5 | 機關 | O-1～O-8 | 變更核定 → 請款收款 → 驗收時間軸 |

無障礙抽查（A-1～A-7）穿插各角色空檔做，三角色各挑一人負責即可。

| # | 操作 | 預期畫面 | 通過條件 | 知道下一步 | 完成任務 | 備註 |
|---|---|---|---|---|---|---|

| C-2 | 看「今日待辦」 | 首頁待辦清單（逾期／今日到期在最上面） | 能說出「我今天最該做的是哪一件」並點進去 | | | |
| C-3 | 進「施工日誌」，選今天 | 日誌表單（出工／機具／材料／工項數量） | 知道今天的日誌還沒填 | | | |
| C-4 | 按「複製昨日」 | 帶入昨日班組／機具／材料，出現「已帶入…請調整今日差異後存檔」 | 知道帶進來的是草稿、還要改今天的差異 | | | |
| C-5 | 填今日工項數量、按「存檔」 | 顯示「已存檔 ✓」 | 手機上找得到存檔鈕（不必捲很久）、按得到（44px） | | | |

| C-7 | 進「現場與品質」→ 缺失分段 | 缺失清單，指派給自己的在最上面 | 知道哪一筆是自己的、下一動是什麼 | | | |

| C-10 | 按「送監造審核」 | 狀態變「監造審核」 | 知道球已經在監造手上，自己不用再動 | | | |

## 七、已知限制（誠實揭露，測試者遇到不算 bug）

1. **表格內的行內輸入在手機約 38px，未達 44px。** W8-0 明文「不重寫表格元件」，把 `<td>` 內輸入拉到 44px 會讓每列高度翻倍、整張表在手機更難用。受影響：施工日誌工項數量、變更明細、請款付款日期／金額、進度排程日期、檢查表量測值與試體強度。
2. **照片縮圖上的刪除／排除 ✕ 在手機為 36px**，非 44px——縮圖本身不夠大，放到 44px 會蓋掉照片主體。
3. **成本、S 曲線、大型報表以桌機為主。** W8-0 明文不要求手機完整編輯這幾面；手機可讀，但編輯請用桌機。
4. **列印頁（施工日誌公定格式、估驗請款佐證包、監造月報）固定亮色版面**，不跟隨深色模式——那幾頁是「紙」，配色以列印輸出為準。
5. **AI 產出一律是草稿。** 照片配工項、施工說明、審查意見、稽核意見都要人覆核；測試者若發現 AI 配錯，請記錄，但那不是本輪的通過／不通過依據。

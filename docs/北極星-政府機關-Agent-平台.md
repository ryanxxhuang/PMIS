# 北極星：政府機關 Agent 平台

> 建立日期：2026-07-28 ｜ 狀態：**長期目標，後續所有開發以此為核心**
> 這份文件不描述現在做了什麼（那看 `docs/AI-Agent-大改版-產品重定位報告-2026-07-25.md` 與 repo），
> 它描述**我們最終要變成什麼**，以及每個功能該怎麼被判斷。

---

## 0. 一句話

> **政府機關的每一個承辦人，都配一個懂他業務、懂他法規、懂他公文格式的 AI Agent。**
> 人只做判斷與簽核；查資料、填表、擬稿、對帳、追期限，交給 agent。

公共工程專案管理（現在做的 PMIS）**不是終點，是第一個垂直領域**。

---

## 1. 為什麼從「工程專案」切入

不是因為工程最好做，正好相反——**因為工程是政府業務裡最複雜的一種**：

| 工程業務具備的特性 | 對應到其他機關業務 |
|---|---|
| 多方角色互相制衡（機關／監造／廠商＝三級品管） | 幾乎所有政府流程都是「承辦→審核→核定」的多級簽核 |
| 契約驅動：期程、罰則、付款條件全部從一份文件長出來 | 採購契約、補助要點、委辦合約，全部同構 |
| 法定期限密集且逾期有法律後果 | 行政程序法期限、公文時效、法定審查期限 |
| 大量重複性文書（日誌、查驗、估驗、月報） | 政府業務的本體就是文書 |
| 需要佐證鏈與防弊（審計、政風） | 所有涉及公帑的業務都需要 |

**只要工程做得起來，其他業務都是它的子集。** 反過來從簡單業務開始，做出來的骨架撐不起工程，之後得重寫。

這是刻意選的難路：**先啃最硬的骨頭，讓平台層被最嚴苛的情境驗證過。**

---

## 2. 核心工程紀律：每個功能都要先分層

這是這份文件最重要的一段。**每寫一個功能，先問它屬於哪一層。**

```
┌─────────────────────────────────────────────────────────┐
│ ③ 介面層 — 每個角色一個 Agent 主控台                     │
│    現場／品管／監造／機關（未來：戶政承辦／社福承辦／…）  │
├─────────────────────────────────────────────────────────┤
│ ② 領域層 — 公共工程專屬                                  │
│    PCCES 標單、估驗計價、ITP、三級品管、施工日誌…         │
│    ← 這一層換一個業務就整個換掉，不要硬抽象               │
├─────────────────────────────────────────────────────────┤
│ ① 平台層 — 所有政府業務共用（★ 真正的資產在這裡）        │
│    身分與多級權限｜契約/法規文件解析｜法定期限引擎         │
│    佐證鏈｜AI 草稿收件匣｜稽核留痕｜AI 模組開關與計量      │
└─────────────────────────────────────────────────────────┘
```

### ① 平台層（要當成產品做，值得多花時間）

| 能力 | 現況 | 為什麼是平台層 |
|---|---|---|
| **多級角色與伺服器端權限** | `project_memberships` + RLS + 狀態轉移 trigger | 任何政府流程都是多級簽核，換業務只換角色名稱 |
| **文件 → 結構化義務** | `parse-contract` / `extract-requirements` → `contract_obligations` | 契約、要點、法規、公文，都是「文件生出義務」 |
| **法定期限引擎** | `contractDue.js` / `penaltyCalc.js` / 機關端法定期限 | 基準日 + 天數 + 罰則，是政府業務的通用形狀 |
| **佐證鏈（evidence graph）** | `evidence_links` / `obligation_evidence` | 「這個結論是哪些文件支撐的」是所有防弊需求的本體 |
| **AI 草稿收件匣** | `agent_actions` + `resolve_agent_action()` | AI 產草稿、人簽核——這是政府採用 AI 的唯一可行形狀 |
| **不可竄改稽核軌跡** | `audit_events`（DB trigger 寫入） | 審計、政風、監察院都要 |
| **AI 模組開關與用量計量** | `ai_features` / `ai_usage_events` / `/admin` | 賣方案、控成本、對機關交代 AI 用在哪 |

**寫平台層時，命名不要帶工程味。** 例如：`contract_obligations` 好過 `construction_deadlines`；`evidence_links` 好過 `valuation_photos`。

### ② 領域層（就大方寫死，不要提早抽象）

PCCES 標單樹、估驗計價公式、ITP 檢驗停留點、自主檢查表、取樣試驗齡期——**這些換一個業務就完全沒用**。
不要為了「未來戶政也要用」把估驗計價抽象成通用計算引擎。**過早抽象比重寫更貴。**

### ③ 介面層（每個角色一個 Agent）

現在是四個工程角色。未來每接一個機關業務，就是「加一組 persona + 一組工具白名單」，
平台層與領域層各自延伸，介面層的形狀不變。

## 3. 四條紅線（違反就毀掉政府客戶的信任）

前三條沿用 `docs/AI-Agent-大改版-產品重定位報告-2026-07-25.md`，第四條是這次新增的。

1. **AI 只產生「草稿」。** 核定、判定、結案、驗收、凍結——agent 的工具箱裡**根本沒有**這些工具。
   靠工具白名單保證，不是靠 prompt 約束。
2. **數字永遠由確定性引擎算。** AI 可以複述金額，但金額必須是 `boqCalc.js` 之類算出來、由工具回傳的。
   AI 不准自己乘除，不准自己編條號。
3. **每個 agent 動作都留痕。** `agent_actions` 記錄角色、種類、目標、理由、佐證、人的覆核結果。
   這同時是稽核軌跡、prompt 調校資料、以及「AI 建議採納率」這個能對外講的指標。
4. **每個 AI 功能都是可獨立開關的模組。**（2026-07-28 新增）
   - 新增任何 AI 功能，一律先在 `src/lib/aiFeatures.js` ＋ `supabase/functions/_shared/aiFeatures.ts` 註冊。
   - 閘門在**伺服器端**（edge function），不是只把前端按鈕藏起來。
   - 每次呼叫都要寫 `ai_usage_events`（功能、使用者、專案、token、成本）。
   - 理由：政府客戶會問「AI 用在哪、用了多少、能不能關掉」；賣方案時要能按功能組合定價；
     出事時要能單獨關掉一個功能而不是關掉整個系統。

## 4. 命名與網域

產品定位既然是「政府機關的 agent 平台」，名稱應該脫離 `PMIS`（那是工程管理系統的通稱，講不出願景）。
方向：`gov agent` 系列。

**2026-07-28 實測（`whois -h whois.nic.ai`，`.ai` TLD 必須指定此 server 才準）：**

| 網域 | 狀態 |
|---|---|
| `govagent.ai` | 已註冊 |
| `govagents.ai` | 已註冊 |
| `agentgov.ai` | 已註冊 |
| `civicagent.ai` / `publicagent.ai` / `govdesk.ai` | 已註冊 |
| `govmate.ai` / `govflow.ai` / `govcopilot.ai` / `govops.ai` / `opengov.ai` / `govstack.ai` | 已註冊 |
| **`gov-agent.ai`** | **可註冊** |
| **`bureauagent.ai`** | **可註冊** |
| **`publicgov.ai`** | **可註冊** |

前次（2026-07-25）調查的工程向候選 `conpm.ai` / `sitesquad.ai` / `constructagent.ai` 仍在清單上，
但**與新定位不符**——它們講的是工程，不是政府。

**現況決議：維持擱置，不購買。** 理由：`gov agent` 最好的幾個字都被搶了，
帶連字號的 `gov-agent.ai` 品牌力弱；與其將就，不如等名稱定案再一次買到位。
（延續 `pmis-domain-naming` 的既有決定；購買任何計費資源前一律先問。）

## 5. 現階段的界線（重要）

**現在只做公共工程。** 這份文件是方向，不是現在就要蓋的東西。具體地說：

| 要做 | 不要做 |
|---|---|
| 寫平台層功能時，命名與資料模型保持業務中立 | 為了假想的其他機關業務去寫抽象層／外掛機制／DSL |
| 新 AI 功能一律走模組註冊與計量（紅線 4） | 現在就去接戶政／社福／採購以外的業務 |
| 遇到「這該放平台層還是領域層」時停下來想三分鐘 | 為了分層漂亮而重構已經在跑的工程功能 |
| 在 PR 描述裡標註這次改動屬於哪一層 | 把 PMIS 現有工程功能改名成通用名詞 |

**判斷準則：** 如果一個設計決定「換成戶政業務也一樣成立」，它就該在平台層，值得多想；
如果「換成戶政業務就沒意義」，它就是領域層，怎麼快怎麼寫。

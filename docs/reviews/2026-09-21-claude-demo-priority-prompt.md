# Claude demo 急件：先做到能順利用

使用者即將 demo，時間很少。本指令優先於上一份完整優化 prompt：先交付以下可用流程，暫緩其餘重構、刪除與擴充。直接實作與驗證，不先寫長篇規劃。

## 第一優先：照片直接填表

在現有施工日誌與自主檢查表頂部放明顯的「上傳照片，AI 填表」。沿用已做好的紙本可編輯表單，不重新設計。

必要流程只有：開表單 → 選照片 → 顯示辨識進度 → 結果直接出現在這張表 → 工程師直接修改 → 存檔 → 重載仍在 → 下載 PDF。

- 不要求跳現場總覽、選批次、接受候選或進 Agent。
- 編輯中補照片不能丟人工輸入；AI 回來不覆蓋工程師已修改的值、不填到已切換的其他文件。
- 已上傳過的照片也能引用填表；不要只顯示重複檔而結束。
- 優先自動帶入工程／廠商名稱、日期、工項、施工敘述、照片可支持的材料／機具描述與可讀紀錄。不要為填滿而捏造完成數量、實測值或合格。
- 自檢照片的雙向尺寸至少要完整呈現在對應的可編輯「實際檢查情形／備註」，保留編號、方向與單位，並能存檔、重載與印出；不要截成單值。若完整數值結構已做好就沿用，否則本輪不要為它冒險重寫整套判定與 migration。文字紀錄不能被當成已通過數值判定。
- 缺來源的必填值就地補，仍允許存草稿。存檔不等於簽署或送出；正式送出沿用現有合法流程，本輪不改整批確認／簽署規則。
- PDF 使用保存後的內容；未存時提供「儲存後下載」，不默默印舊值。草稿清楚標示未簽署。
- 發生辨識失敗要保留照片與人工內容，顯示重試和直接手填；不能卡死整張表。

## 第二優先：介面只留三核心

廠商只看到「施工文件」「契約與提醒」「估驗請款」。隱藏問 GovAgent、Copilot、聊天與非核心工作入口；不要讓它們在背後持續自動發出 Agent 請求。保留三核心使用的照片與契約 AI。

先改可見入口和必要路由行為，不進行全庫刪碼、不刪正式資料或遠端資源。必要查驗／送審操作仍要從核心流程進得去。監造查驗與日誌不作為廠商填寫入口。

## 第三優先：檢查已有契約、估驗流程

- 契約上傳 → AI 整理 → 顯示何時做什麼、原文依據。沿用既有頁面與引擎，不重寫；只修會阻斷 demo 的問題。缺期限依據明示待補，抽取失敗能重試，不顯示假的成功。
- 估驗沿用監造確認量：未確認不能請，確認後才出現可請量。不要拿施工日誌／AI 草稿繞過監造。若沒有已確認資料，用隔離測試案完成真正確認流程，或使用清楚標示的示範資料，不偽造正式紀錄。

## 執行與 demo 驗證

先看目前 main、執行中分支與既有修改，避免覆蓋。模型分工沿用使用者指定：低風險 opus5.2，高風險 fable5.1；別名不可用如實說明，不把 coding 模型名稱改進產品 API。

先驗使用者實際要開的站點。若是無後端 demo 模式，必須明說目前不能真上傳／持久保存，改以具備後端與合法測試帳號的隔離專案展示；不能拿種子資料宣稱即時 AI 辨識成功。

把以下當成交付門檻，完成後停止擴張範圍：

1. 用 PMIS 現有真實照片，在真後端測試案從兩種表單內上傳、看到填值、直接改、存檔重載及下載 PDF。已有 Anthropic 外傳授權，金鑰不得輸出。只跑必要次數，不重新大量測模型。
2. 確認補照片不丟修改、失敗可重試；廠商看不到 Agent／監造填表入口。
3. 契約提醒與監造確認後估驗各走通一次既有流程。真實辨識、快取、示範資料要分清楚。

跑 repo 要求且與變更相符的檢查；不因趕時間跳過權限或資料保存驗證，也不新增龐大測試矩陣。部署依既有授權，完成後在實際 demo 網址再核對，不能只說本機通過。

最後只回報：可開啟的 demo 網址／測試案、最短操作順序、實際驗過哪些、仍有哪些會卡住。沒跑過不要寫「全部完成」。若時間不足，先交付已跑通的照片填表流程，明確列出其餘狀態；不拿臨時假按鈕或假 AI 結果湊齊三核心。

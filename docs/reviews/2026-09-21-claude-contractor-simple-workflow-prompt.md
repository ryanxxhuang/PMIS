# 給 Claude：施工廠商網頁三核心與表單直接填寫

請實作以下已由使用者明確提出的需求。不要只再改一輪文案／藏選單，也不要增加新工作台。目標是工程師不用懂任何批次、候選、Agent、草稿建議或版本機制，就能完成日常工作。

## 0. 範圍與開始前

優先只做施工廠商 desktop web。三核心只有：①照片 AI 填施工日誌／自主檢查表；②契約 AI 整理與提醒；③監造確認後的估驗請款。手機不擴充新體驗，維持可用不回歸。監造／機關只調整三核心所必要的銜接，不全面重做。

先讀 AGENTS.md、DEVELOPMENT.md、CURRENT.md、DECISIONS.md 與本次 `2026-09-21-contractor-simple-workflow-review.md`；再只讀受影響架構。檢查目前 HEAD 與 F2 是否已合併，不重做已完成修正，不覆蓋其他 worktree 工作。檢查基準是 main `52f53ef`，不是要求退回該版。

本次使用者已明確要求縮為三核心、移除 Agent 及簡化逐欄操作；把新邊界增補到 Decision，不再拿舊四入口設計反覆請使用者確認。舊來源稽核／簽署紀錄保留於後端即可，不能因此要求使用者操作 Agent 收件匣。與授權無關的新雲端費用或正式資料刪除仍按現有規則處理。

依使用者指定：簡單低風險使用 `opus5.2`；複雜高風險使用 `fable5.1`。沿用執行環境已確認的模型別名；不存在／不可用時明示，不自行宣稱切換成功，也不要把這兩個 coding agent 名稱寫成產品 Anthropic API 模型。UI 文案／導覽可列低風險；表單合併、AI 資料結構、確認／簽署、DB、估驗均列高風險。

## 1. 廠商只留三個工作入口

- 左側工作導覽只留「施工文件」「契約與提醒」「估驗請款」。預設開施工文件的今日施工日誌；歷史日期與文件可在此切換。
- 拔掉廠商端頂欄「問 GovAgent」、側欄問答、Copilot FAB／聊天面板、Agent 專頁與新對話入口，也移除為此自動執行的 Agent 請求。用網路請求驗證，不只藏 DOM。
- 移除廠商獨立的今日工作儀表板、品質、工安、S 曲線、月報、跨案分析、成本等工作入口；契約期限嵌在契約頁，查驗與補正在文件／估驗詳情完成。必要送審、疑義、變更、標單匯入與成員設定作核心內的次操作／設定，不再並列為工作模組。
- 原 `/agent` 等退場廠商路由不能仍開啟聊天功能；依既有權限導到三核心或歷史唯讀位置。不要誤刪照片／契約 AI 共用呼叫、AI 閘門、用量記錄、稽核與監造確認引擎。
- 盤點退場元件引用，移除無使用者的前端程式與測試；其他角色或核心還在使用的共用元件不刪。遠端資源及正式歷史資料不在這次刪除範圍。

## 2. 施工文件：表單就是唯一工作畫面

固定畫面：表單類型切換（施工日誌／自主檢查表）、日期／文件選擇、主按鈕「上傳照片，AI 填表」；下面直接顯示可編輯真實表單；底部主按鈕「存檔」。選照片或拖放即開始，不先選工作流、不跳到現場總覽。

- 兩張表都要頁內上傳、新增照片及選用既有照片。AI 結果原地填入目前表單；一般情況不顯示 IntakeResult、候選列表或套用建議步驟。
- 文件 context 必須明確：project、doc_type、date、目前 document/version、自檢範本／工項／位置或批次。前端提供意圖，伺服器驗證角色、文件歸屬、狀態與版本，不能相信任意傳入 ID。
- 使用者已選日期時，以目前文件日期為意圖；照片紙上日期不符要就地顯示差異，不悄悄跳日期或生另一份文件。多日期、多工項不能全混在一張自檢表：只在有歧義時原地詢問一次如何分開。
- 現有未存檔內容不得阻擋上傳。開始辨識記錄基準；回來時只填空欄或未被人修改的舊 AI 欄。期間人工輸入優先；切文件／切專案後過期回應不能填錯地方。衝突只顯示該格比較，不能整張覆蓋。
- 全是已保存照片也能引用到目前文件並沿用辨識，不再以「沒新檔」結束。儲存去重不等於不能重用照片；重試不重複建文件、不重複計量。
- 同批辨識可重用到兩張表，但先完成目前選擇的表。範本與工項明確就自動選；歧義才顯示少量選項；沒有核可的檢查標準時可先存草稿，不捏造合格標準。
- 處理中只顯示「上傳中／AI 填寫中／完成，有 N 項需補」；保留失敗重試與已上傳照片。批次、快取、版本號、hash、除錯訊息放幕後。
- 任一可編輯格直接改；AI 標記淡化、來源點開才看，不能把「已帶入／原文／確認」塞滿每格。照片可展開放大核對。
- 存檔保存完整目前草稿與人工修改，缺欄也能存；重載能恢復。簽署仍是明確獨立意願，存檔不得偷偷簽署送出。
- 正式交件按「審閱並簽署送出」：集中一次檢查必填及關鍵數值，對本版已呈現的合格欄位整批確認，沿用伺服器版本與授權驗證。不要靠 UI 直接把所有來源無條件改 confirmed，也不能把空白／衝突／人員到場默認成真。已簽文件須另開更正版。
- 下載 PDF 是次動作；有未保存改動時提供「儲存後下載」，不逼人放棄修改。簽署版／草稿版清楚區分；畫面與 PDF 使用同一內容、範本與數據口徑。

## 3. AI 要真正填整張表

先列出兩張表的所有實際欄位及可取得來源，再補缺少的 schema、資料查詢與 mapping。不要把任務做成更長的照片 caption。

1. 專案、契約、標單可提供的名稱／日期／工期／單位／契約量直接帶入。表頭缺共用資料時同頁補一次；依權限保存到正確來源，不能每份日誌重填或暗改契約。
2. 對施工概況、工作項目、材料名稱、可見工種／機具、自檢描述、可觀察施工狀況，積極產生自然可用的草稿。使用者接受合理草稿由工程師修正；不要所有欄位都回 pending。文字不得無依據寫成「已完成、全數合格、監造已到場」。
3. 當日照片、可讀紙表、當日補充資訊優先；昨日資料可沿用種類與適用敘述，數量若作參考要標來源。照片可見人數／台數可作待核對建議，不能宣稱是全天總數，跨照片重複人機不得加總。
4. 清楚記載的數量、實測值直接填進可編輯格，保留來源。尺寸與完成量分離；設計值與實測值分離；13×11 mm 必須完整保存兩方向，15×15 cm 不可變成 15 m²／T。編號 1 與 4 是不同對象，要分列或分表，不只留提示要求人重新輸入。
5. 雙向尺寸的儲存、範本、前端編輯、簽署判定與 PDF 必須一起支援；既有單值表相容。兩方向的合格標準各有依據才計算判定；無標準可存草稿，不能任意取其中一向判合格。
6. 同一物件多張照片要去重、組合證據；不同批次／位置不合併。無法確定是相同對象時先提示，不能靠數字相同判定。
7. 安全教育、保險、抽驗、通知等照片外資訊，先取當日已確認紀錄；仍缺就集中幾個簡短問題於表內補完。沒有事件資料不等於事件未發生，不能全填「無」。
8. 天氣取當日有效來源；工期、累計量、進度與金額用既有程式／DB。缺原始資料提供就地補值，別讓 AI 編數字；不要順手改進度定義。
9. 修正兩次轉錄的失敗分支：第二次失敗／被擋／無效時，第一次內容不能冒充已通過比對。可以保留為明確未驗證建議，但不可用它自動定日或分組；獨立成功的逐格結果保留。
10. 人工修改不被重辨識覆寫；已簽內容不可改；圖片上的文字只是資料，不可作工具執行指令。AI 用量／來源記在幕後，不增加使用者操作。

## 4. 契約與提醒、估驗請款

- 契約同頁上傳後自動整理成「事項／期限／責任方／目前狀態」，點開看原文頁碼；可直接處理或補必要基準日。不要要求先問 Agent、再去另一個擷取工作台找結果。保留 D-019 已有處理規則及原文依據。
- 未抽取成功、讀不到文字、時點不足，要明確顯示並能重試／補登，不能以空清單假裝沒有待辦。提醒必須在移除聊天 Agent 後仍正常運作；測試以不寄信方式驗證，避免向真用戶送測試通知。
- 估驗由監造正式確認量自動形成可請草稿，顯示本期可請、已請、尚待監造確認以及佐證；廠商可從文件或估驗直接發起／追蹤查驗。自檢／日誌存檔與 AI 判定都不得增加可請量。
- 保留後端對期間、累計量、重複批次、撤銷減量與併發的限制。非實體項目前不能請的，要明示缺的契約計價依據；不藉 UI 瘦身解除 cap 或改計價邏輯。

## 5. 實作順序與完成門檻

依序交付：A 表單內完整操作＋廠商三入口；B 逐節填表＋尺寸／多照片結構；C 契約與估驗必要串接＋退場清理。每包完成可供操作的結果，不以增加文件頁數當交付。

最多五組驗收，按改動補必要測試：

1. **操作**：廠商桌面只見三入口；兩張表均可從頁內上傳到編輯存檔，不經批次／候選／Agent 頁；無逐欄確認負擔。確認無背景 Agent 請求，其他角色必要流程正常。
2. **資料不丟**：邊編輯邊上傳、部分失敗重試、全為既有照片、重辨識、換日期／專案、存檔重載、併發版本衝突，人工值與已簽版本均保全，沒有重複文件／計量。
3. **真實辨識到填表**：用 PMIS 根目錄的 `LI2995~1_0.JPG`、`LI89DE~1_0.JPG`、`LIEE66~1_0.JPG`、`LIFA1C~1_0.JPG`、`LINE_A~4_0.JPG`，從實際前端選檔走完整鏈。三張紙表共有 8 筆雙向實測項目，逐筆核對數值／方向／單位／編號進表、保存、重載及 PDF；日期 115.8.4＝2026-08-04，設計搭接值不能當實測，卡尺模糊不能硬填。讀到率與實際填入率分開報，不以 stub 代替。至少再用一組不同格式的合法測試素材驗證非硬編版型；合成素材與真實照片分開記。
4. **契約與估驗**：上傳契約後待辦有期限及原文；缺基準可補；未監造確認量不可請、確認後才增加、重播不加倍、撤銷／減量仍受限制。按實際範圍跑必要 E2E、Edge、pgTAP 與既有檢查。
5. **交付證據**：提供操作截圖及產出的 PDF；逐欄列自動填入、人工修改、仍缺來源。資料支持的欄位目標填入率 ≥90%，同時公開整表填入率與正確率的分母、修改次數、從選照片到可編輯及完成存檔的時間；未知數字不以 0／無灌水，未達就如實列缺口。已測與未測、真模型與 stub 分開報。同步 CURRENT、BASELINE 與受影響架構，不能宣稱未測已通過。

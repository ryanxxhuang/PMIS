## 2. 本階段補齊（U11 與文案）

- 送審、疑義、變更設計三頁的關鍵字與分段篩選改存 URL（與提醒中心同一個 `useUrlFilters`），從單據返回、重新整理、分享網址都保留；只放關鍵字與分段，不放表單或敏感內容。
- 日誌待辦直達當日（`/site-log?d=`），切日期時 URL 跟著改。
- 深連結指到不存在的單據：四個清單頁顯示「找不到指定的…已顯示清單預設的一筆，網址已改為不指向該筆」，並把失效參數從 URL 移除，不再默默改選另一筆卻讓網址仍指原單。
- 從單據返回今日待辦但原項已離開清單：顯示「剛才處理的事項已不在這份清單，可能已完成或已交給對方」。
- 文案：機關首頁角色摘要「辦理核定與付款」改為「辦理核定、登錄付款紀錄」；其餘核對見 §4。

## 4. 文案核對

| 詞 | 現行含義 | 核對 |
| --- | --- | --- |
| 存檔 | 日誌／檢查表寫入資料庫；「已存檔 HH:MM」為本次寫入時刻 | 未存檔／存檔中／已存檔三態；本地暫存不稱已存檔 |
| 提送 | 送審建立紀錄即「已提送」；文件本體另上傳 | 表單與詳情明示兩步 |
| 受理 | 監造把送審／變更從已提送／提出轉為審核中 | 受理段與審定段分開 |
| 核定 | 監造核定估驗；機關核准／駁回變更 | 變更頁核准／駁回加確認框；送審核准／核備由監造 |
| 結案 | 疑義由廠商確認結案；缺失由監造複查結案 | RFI 提示不再承諾「追問」 |
| 草稿 | AI 帶入的日誌內容、AI 審查意見；人確認後才寫入 | 「AI 草稿」標記與「結果只保留在本頁」 |
| 付款 | 系統只登錄請款／收款紀錄 | 頁首、角色提示、首頁摘要皆改為登錄紀錄 |

角色提示不再取代案件脈絡：驗收頁與請款頁以 `keepSubtitle` 保留專案名稱／頁面說明。

## 5. 三角色真人測試腳本與記錄表（尚未執行）

每角色 2–3 位實際使用者，桌機瀏覽器 1280 px 以上，Demo 或測試專案。不提示按哪裡；施測者只記錄，不引導。

| 角色 | 任務（唸給受測者） | 成功條件 |
| --- | --- | --- |
| 廠商 | 「填今天的施作量並加一張照片，然後告訴我哪些已經存了。」 | 說得出已存檔／未存檔；找到存檔與照片入口 |
| 廠商 | 「自主檢查填到一半去看查驗紀錄，再回來完成並申請查驗。」 | 未丟輸入；申請後說得出等監造 |
| 廠商 | 「提送一份文件，再處理一件被退回的送審。」 | 說得出紀錄已建立但文件未附；找得到再送 |
| 監造 | 「找一件廠商補正再送的送審，看完資料後決定受理或退回。」 | 說得出為何輪到自己、上次退回原因；受理與退回分得清 |
| 監造 | 「開一件待查驗，判不合格，再去看產生的缺失。」 | 找得到缺失入口 |
| 機關 | 「找一件待核定的變更，說明它的影響，然後決定。」 | 說得出淨額、核准後金額、哪些資料系統沒有 |
| 機關 | 「登錄某一期的收款，中途我會讓它失敗一次。」 | 說得出哪個值已存、哪個沒存 |
| 機關 | 「先只填驗收日期就登錄，再補結果。」 | 第一次被要求選結果 |

記錄表（每人每任務一列）：能否獨立完成／第一次點擊／繞路或求助次數／是否說得出「已保存」與「下一責任方」／操作錯誤／用時（碼表實測，不預設目標）。滿意度不記分，只記原話。

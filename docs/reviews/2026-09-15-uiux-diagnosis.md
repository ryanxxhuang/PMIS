> 本報告不是實作、合併或部署授權，不取代既有 Decision。使用者指定階段後，才由 Claude Code 執行該階段。
> 程式檢視基準：`7156aeff2ef21789f422fdab4739426072849cec`。後續實作前須重新確認問題仍存在。

> **最新範圍調整：為減少工程量，本輪僅優化桌機網頁版的機關、廠商、監造流程。手機、平板及其他裝置的專屬設計、響應式優化、觸控與跨裝置接續延後。下文保留的行動裝置現況是診斷證據或後續候選，不是本輪實作及新增驗收要求；以 prompts 共通規則第 14 條為準。**

## 1. 判斷與建議順序

目前最需要改善的是「工作如何接續」，而不是再換一套視覺風格。功能已相當完整，也有共用介面；但使用者仍需要理解模組分類、記住跨頁路徑，並自行判斷何時已存檔、誰接手、下一步在哪裡。

三個角色不應只得到同一套選單的不同權限版本。廠商需要快速完成填報與補正；監造需要對照證據、形成意見、交接審查；機關需要掌握責任、影響與核定依據。這是三種工作重心，不是新增三套系統。

建議依序處理：

1. **先修會讓人誤判結果或丟失輸入的操作**：驗收未選結果卻送出合格、送審／疑義失敗仍收起表單、AI 結果可離頁查看的承諾。
2. **整理找工作與返回工作的方式**：入口層級、初始化與待辦的關係、搜尋與 AI 的區別。
3. **廠商**：讓填報、檢查、提送、補正成為可接續的操作。
4. **監造**：讓待審案件進入後，能完成「看資料 → 留意見 → 作決定 → 接下一件」。
5. **機關**：讓變更、金流、驗收的關鍵資訊與操作結果清楚可核對。
6. **最後統整桌機網頁版的返回狀態、文案與真人驗收**；手機與平板另期處理。

不建議先全面修改色票、圓角、字體、動畫，或另造工作流程引擎。這些不會解決目前最具體的操作斷點。

## 2. 證據與限制

本次以程式、現行規範及本次對話前段的本機 Demo 操作為依據。前段曾檢視機關桌機待辦／請款，以及廠商手機首頁，也執行既有三角色流程測試。這些只支持特定畫面與路徑的判斷。

使用者澄清交付形式後，補充瀏覽被瀏覽器的管理政策驗證機制阻擋，沒有繞過；後續以唯讀程式檢視完成診斷。**未完成三角色所有頁面的逐頁視覺走查、正式資料實測、真人訪談或操作時間量測。** 報告不把推測描述成已觀察到的真人行為，也不宣稱效率提升百分比。

證據標記：

| 標記 | 意義 |
| --- | --- |
| 程式確認 | 可由目前控制流程、介面文案或資料保存位置確認；不等於正式環境已重現 |
| 操作觀察 | 本次對話前段在本機 Demo 走過的有限路徑 |
| 設計判斷 | 根據目前介面提出的改善方向，需要原型或真人任務驗證 |
| 待實測 | 必須有真後端、指定資料或真人操作，才能判斷影響範圍 |

優先級用於排程：P0 是可能造成錯誤業務結果或輸入遺失的操作；P1 是主要流程的阻礙；P2 是一致性與辨識改善。這不是資安嚴重度評分。

## 3. 三角色應有的主要工作路徑

以下是建議的使用體驗，沿用既有角色、資料及狀態轉移。

| 角色／情境 | 建議路徑 | 使用者完成後應看懂什麼 |
| --- | --- | --- |
| 廠商：每日現場填報 | 今日工作 → 選日期 → 施作數量／照片／必要紀錄 → 檢查未完成項 → 存檔 | 哪些已保存、哪些只是 AI 草稿、照片是否成功上傳 |
| 廠商：品質交接 | 自主檢查 → 檢視判定 → 沿用紀錄申請查驗 → 等待監造；不合格則處理缺失 | 送出了哪張單、檢附哪一版證據、現在由誰處理 |
| 廠商：送審與補正 | 新增送審 → 核對提送資料／附件 → 查看監造意見 → 補正 → 再送 | 是否已正式提送、附件是否完整、版次與待回覆對象 |
| 廠商：估驗請款 | 建立期別 → 帶入日誌數量 → 核對佐證 → 送監造 → 核定後接請款 | 日誌存檔不等於估驗送出；監造核定後才進金流登錄 |
| 監造：審查 | 現在輪到我 → 指定案件 → 本次內容與附件 → 既有意見／補正 → 受理或審定 → 返回原佇列 | 目前是受理還是核定、意見是否保存、球交給誰 |
| 監造：查驗／複查 | 待查驗 → 現場及自檢佐證 → 判定 → 缺失改善 → 複查結案 | 不合格與缺失建立的結果各自清楚；不可用一個成功訊息掩蓋部分失敗 |
| 機關：變更決策 | 待核定變更 → 原案與變更差異 → 金額／工期影響及現有審查資料 → 核准或駁回 | 核定對象、影響、狀態及後續處理者 |
| 機關：金流追蹤 | 已核定期別 → 本期應領／登錄資料 → 確认欄位變更 → 保存結果 | 當期與全案金額分清楚；畫面紀錄不等於系統真的執行銀行付款 |
| 機關：驗收 | 當前階段 → 前置條件／責任方 → 明確選結果及日期 → 登錄 → 下一階段 | 未選結果不能等於合格；系統記錄不等於代替人作驗收判定 |

監造核定估驗；機關核定變更設計。不要把所有頁面的動作一律改叫「審批」，也不要把機關當成所有流程的最後簽核人。

## 4. 問題清單與改善方式

### U01｜P0：驗收畫面空白結果，送出時卻變成合格

**證據：程式確認。** `Acceptance.jsx` 的結果選單有空白選項；`StageRow.save` 用 `result || '合格'`，登錄鈕僅檢查日期。

- 操作：在需要結果的階段只填日期，不選結果，再按登錄。
- 影響：畫面沒有表達使用者選了合格，送出的資料卻包含合格。這是明確的互動與資料語意不一致。
- 建議：結果必須明選；就近顯示必填提示；提交處再次檢查。登錄前能核對階段、日期、結果；取消及失敗保留輸入。
- 驗收：未選結果不發寫入請求；明選不合格仍走既有改善／複驗推導；不改期限計算或三方權責。
- 階段：1。不是要求重做既有驗收時間軸。

### U02｜P0：新送審／新疑義失敗後仍關閉表單

**證據：程式確認。** `Submittals.jsx` 與 `RFI.jsx` 的 `submit` 都是 await 建立後直接 `setForm(null)`；`store/slices/collab.js` 的建立函式可能回傳 `{ error }`，頁面未檢查。

- 操作：填好資料後提送，後端回傳失敗。
- 影響：表單消失，已填內容失去目前的編輯入口，使用者可能誤以為成功或被迫重填。
- 建議：成功才收表單並定位新紀錄；失敗保留輸入與圖面標註、顯示可重試錯誤；送出中防止重複提交。
- 驗收：用失敗回應重現，不只測正常 Demo；錯誤不出現成功提示；重試一次只建立一筆。逾時但伺服器可能已成功的情況須先查現有去重能力，不以 UI 假裝保證冪等。
- 階段：1。

### U03｜P1：AI 宣稱可離頁回來看，畫面結果卻只放在頁面狀態

**證據：程式確認。** 送審頁顯示「可離開此頁稍後回來查看」，但 `aiRead`／`aiReview` 存在頁面的 `useState`；讀文件函式回傳結果，頁面沒有載入歷史結果的還原流程。

- 影響：離頁後找不到剛才結果，可能重複執行；這不等於後端完全沒有稽核紀錄，但 UI 沒有提供承諾的續看體驗。
- 建議：近期先讓文案符合現有能力，說清結果保存範圍及離頁後果。若要真正支援背景工作與續看，另提完整結果持久化、錯誤與重試方案。
- 驗收：離頁／重進的實際行為和文案相符；不假顯示背景完成；兩個 AI 按鈕說明各自讀了哪些資料。
- 階段：1 修正承諾；4 整理審查助手位置。新增背景任務不包含在前端改善授權內。

### U04｜P1：導覽入口重複，群組名稱與實際動作不總是一致

**證據：程式確認＋設計判斷。** 工作群組、群組子頁、頁首 `PageTabs`、角色常用入口、手機底欄及功能尋找同時存在。側欄群組文字導向首個子頁，旁邊箭頭才展開。平板側欄收合後又依賴頁內分頁找到同組功能。

- 影響：使用者要學會哪些元素是分類、哪些是工作、哪些是畫面切換。重複本身不一定錯，但目前缺少跨尺寸一致規則。
- 建議：保留「待辦」為主要入口；三個角色常用工作作捷徑；完整功能有固定入口。群組展開與導航用一致互動，不讓同一標籤在不同位置有不同意思。
- 本輪先決定：桌機網頁版由哪一個元件承擔同組導航；手機與平板方案延後。D-015 的「內容區不重複子頁導覽」與現況 `PageTabs` 有衝突，先記錄設計決策，再改程式。不能直接刪掉平板目前唯一可見的子頁入口。
- 本輪驗收：三角色在桌機網頁版都能找到其合法功能，側欄展開／收合時入口可達；既有深連結及權限不變。
- 階段：0 定案、2 實作。PR #83 已補捷徑和尋找功能，先評估，不重做。

### U05｜P1：未匯標單時，初始化取代整個待辦內容

**證據：程式確認；真案影響待實測。** `Dashboard.jsx` 在 `!imported` 分支只渲染初始化；即使待辦引擎能產生不依賴標單的送審／疑義／履約事項，正常工作清單也不在此分支顯示。

- 影響：新案使用者可能被要求完成設定，卻看不到已可處理的工作；一般成員也不一定有完成設定的權限。
- 建議：把設定視為有責任人的準備事項，與已可執行的工作並存；只對真正依賴標單的功能提示前置條件。保留建案第一站為專案文件及正式模式既有規則。
- 驗收：用「無標單但有送審／疑義」資料驗證；管理者有準備入口，一般成員知道由誰處理；不能因此把 Demo 工項寫入真案。
- 階段：2；若發現權限／正式模式規則需改，列為獨立產品決策。

### U06｜P1：廠商的提送與附件準備分成兩段，容易誤解完成程度

**證據：程式確認＋設計判斷。** 新送審表單先建立 `已提送`，只有附件說明，文件上傳在建立後詳情內；提示仍提到文件另以公文／雲端連結提送，但既有詳情已支援上傳文件。

- 影響：按「提送」後，使用者可能以為整份文件已送出；監造看到已提送，仍需判斷文件是否到齊。
- 建議近期版：建立成功立即進該件詳情；清楚區分「提送紀錄已建立」與「文件附件狀態」；把下一步上傳、外部提送說明放在同一區域。補正時先看退回原因、目前附件及版次，再進再送。
- 不要偷改：將流程改成「草稿 → 附件完整 → 正式送出」會動到可見時點、狀態機及業務責任，不是加一個步驟 UI 就能完成；列為另案選項。
- 驗收：建立、附件失敗、補正再送各有真實回饋；不因補上附件自動再送或核准；保留版次歷史。
- 階段：3。

### U07｜P1：品質分段切換會卸載編輯器，未保存工作容易中斷

**證據：程式確認。** `Quality.jsx` 條件渲染五個分段，部分佇列點擊用 `key={queueTick}` 重新掛載；`ChecklistSection` 的實測值、位置及修訂原因放在子元件本地狀態。

- 操作：開始填檢查表，切到查驗／缺失，再回檢查表。
- 影響：未保存值隨編輯器卸載而消失；需要瀏覽另一段資料時特別容易碰到。
- 建議：先在該編輯流程提供離開防護或同頁暫留；有更廣需求再設計草稿保存。路由參數記住分段與選取，不讓一般導航強制重掛編輯中的元件。
- 保留：既有自主檢查接查驗、版本修訂、自動判定與缺失關聯。不是新增第二套品質流程。
- 驗收：跨分段／點佇列／切案三種情況都不靜默丟輸入；取消離開可繼續填；切案不得帶入前案草稿。
- 階段：3。

### U08｜P1：監造需要工作導向的審查順序，不能只依按鈕集合完成判斷

**證據：設計判斷，建立在已存在的詳細頁上。** 送審已有附件、意見、兩種 AI 助手、受理與審定；疑義已有問答／結案；變更已有監造受理與機關核定。問題不是缺少這些功能。

- 建議：詳情開頭先回答「現在為何輪到我、本次新增／補正了什麼、下一個合法動作」；接著提供文件與現有歷史；審查意見與作決定放在同一工作脈絡。AI 為可選輔助，標明資料範圍、未覆蓋項與人工責任。
- 完成後：留存剛才結果及交接對象，提供返回原篩選或明確的下一件入口；不在核准瞬間自動切到另一筆，避免誤操作。
- 驗收：受理不是核准；退回不是終局駁回；使用者能對照既有補正與附件；沒有 AI 仍可完成審查。
- 階段：4。先以送審做完整示範，再將確有第二使用點的互動套到疑義／查驗。

### U09｜P1：金流欄位離開即寫入，保存語意與其他流程不同

**證據：程式確認。** `Payments.jsx` 的請款日、收款日、實收金額各用 `onBlur` 寫入；頁面有錯誤橫幅、前置限制及溢收確認，但缺少每次欄位保存的持續狀態。PR #83 指定期別後表格只顯示該期，統計與匯出仍為全案。

- 影響：使用者不容易知道剛才只是離開欄位，還是已改了正式紀錄；當期與全案範圍也需要更清楚區隔。
- 建議近期版：保留現有寫入方式，明示「離開欄位後儲存」，提供儲存中／已儲存／失敗與重試；日期驗證失敗時畫面值與正式值須可辨識；全案統計和當期期別用明確標題分區，匯出明示全案範圍。
- 可選後續：改為一個期別編輯後明確儲存。先確認既有 API 能否一致處理欄位相依；不可用三次 request 假稱單一交易，也不可自行改付款權限。
- 驗收：成功、失敗、超額取消、無收款日、指定不存在期別均有清楚結果；金額公式不變；不宣稱完成銀行付款。
- 階段：5。

### U10｜P1：機關決策資料要聚焦「這次要決定什麼」

**證據：設計判斷。** 變更詳情已有差異、金額和狀態；驗收已有時間軸與前置條件。仍應以承辦決策順序重新排列，而不是另加一堆首頁統計卡。

- 建議變更：頁首呈現本件事由、既有金額／工期影響、目前階段與責任方；差異表與現有依據緊接其後，最後才是核准／駁回。缺的審查意見必須顯示未提供，不能由 AI 補成正式意見。
- 建議驗收：進入先定位目前待辦階段，先看前置條件及誰能登錄，歷史階段仍可展開。日期、結果、備註形成一次可核對的操作。
- 驗收：機關能指出目前核定哪張單／哪階段及已知影響；沒有資料的地方明確揭露；監造不能看到機關專屬核准動作。
- 階段：5；U01 不等此階段才修。

### U11｜P1：回到工作的位置仍不一致，部分待辦只到頁面

**證據：程式確認。** PR #83 已為首頁保留 URL 篩選及多種深連結；但提醒中心、送審、疑義仍各有頁面本地篩選。提醒中心傳遞返回網址時，網址不含其本地篩選。日誌與驗收待辦仍指向頁面，未帶日期／階段。

- 影響：使用者從提醒去做事，返回後可能又要重找；不同入口的完成閉環體驗不一致。
- 建議：先定義每種工作需要保留的專案、篩選、選取及定位；只將可分享且非敏感的識別／篩選放 URL，不把未保存文字或附件放入。到驗收定位特定階段，到日誌定位該工作日期。
- 驗收：返回、重新整理、無效 ID、完成後原項離開篩選、切換專案都可理解；不能默默改選另一筆讓使用者以為仍是原單。
- 階段：2 處理入口，6 補齊跨流程。

### U12｜P2：功能搜尋、資料查詢與 AI 問答的期待不同

**證據：程式確認＋設計判斷。** 現有尋找功能是本地頁面檢索；頂欄搜尋入口送往 `/agent`，另有側欄及浮動 AI 入口。頂欄可見文案已說「問 GovAgent」，但 aria-label／圖示仍帶搜尋語意。

- 建議：明確命名「尋找功能」與「問 GovAgent」，列出各自能做什麼；一般找頁面不能依賴 AI。相同尺寸內減少等權重重複 AI 入口。若未實作跨資料搜尋，不承諾可直接搜尋到每張單據。
- 驗收：使用者找請款頁與問契約問題各有可預期路徑；AI 關閉不影響功能導航；鍵盤與報讀器名稱一致。
- 階段：2。

### U13｜P2：角色提示不能蓋掉案件脈絡，也不能描述不存在的動作

**證據：程式確認。** PR #83 的 `PageHeader` 以角色提示優先取代 subtitle；驗收原本含專案名稱的 subtitle 沒有 `keepSubtitle`。RFI 廠商提示寫「有疑問可繼續追問」，目前詳情動作是廠商確認結案、監造補充回覆，並沒有同筆廠商追問動作。

- 建議：頁面脈絡與角色指引分開處理，脈絡資訊不被通用文案取代；指引只描述當前合法且實作的動作。機關的付款提示也應明確說是紀錄登錄。
- 驗收：專案、期別、文件原文優先等資訊仍可見；每個動作承諾都能對到入口及既有權限。
- 階段：1 核對新文案；6 做全案一致性驗收。

### U14｜P2：長表單及手機應按工作性質安排，不能只縮小桌面

**證據：程式確認＋設計判斷；現場真人效果待測。** 日誌已有照片、複製昨日、AI 草稿、dirty 保護與貼底存檔，但公定欄位預設展開；品質又有五種分段。手機辦公室表格頁則受現行唯讀規範限制。

- 建議日誌：日期與保存狀態固定可辨識；本日數量／照片與必要填報優先，依工作將完整公定欄位分區展開。未完成必填不可藏到使用者找不到；列印輸出維持完整。
- 後續候選（本輪不做）手機：現場填報、拍照、查驗詳情專注完成一件事；不能辦理的桌面操作說明原因並保留同筆連結，讓使用者在桌機接續。不要為了「手機可完成所有待辦」擅自開放估驗／金流表格編輯。
- 本輪驗收：桌機長表單可清楚找到主要動作，長文字與附件失敗可讀，列印及表格功能不受損。手機／平板的底欄、虛擬鍵盤與觸控驗收延後。
- 階段：3 的桌機日誌、6 的桌機整體驗收；手機／平板另期處理。

## 5. 資訊架構：哪些保留，哪些改呈現

這是候選配置，不是要求重新命名所有路由。第 0 階段先以現有介面畫出桌機網頁版入口草圖後定案，其他裝置草圖延後。

| 功能範圍 | 建議位置／呈現 | 處理方式 |
| --- | --- | --- |
| 現在輪到我／等待對方／今天已完成 | 工作起點 | 保留既有收件匣；「今天已完成」僅涵蓋可靠時間戳的資料，不能補假數量 |
| 角色常用三入口 | 桌機捷徑；手機底欄延後 | 評估 PR #83 配置；機關是否每天需要驗收、監造是否每天需要報表，用任務測試決定，不加偏好設定系統 |
| 日誌、品質、工安、停留點 | 現場工作 | 保留各自資料責任；增加有上下文的接續入口，不能合併品質／工安的正式紀錄 |
| 送審、疑義、變更 | 審查協作 | 清單模式一致，詳情按各自狀態機安排，不能把受理／核備／核定混成單一按鈕 |
| 估驗、請款、成本、進度、排程 | 進度與金流的完整工具 | 保留；以期別、工項連接，成本與排程維持廠商權限 |
| 月報、監造報表 | 工作成果／報表 | 從相關工作可進入；選單保留；避免為了與驗收同一群組而強行串成順序 |
| 驗收 | 結案階段工作 | 保留時間軸，待辦直達當前階段；不另做第二個驗收首頁 |
| 專案文件、契約重點、期限 | 文件來源與履約 | 檢視來源、查看要求、追蹤執行清楚區別；契約兩步導引後補適當的期限接續，沿用既有資料鏈 |
| 提醒中心、風險稽核、活動紀錄 | 查核／追蹤 | 說明涵蓋範圍；不宣稱三個列表等價，不為畫面數字一致而重算第二份到期規則 |
| 跨案總覽、三方成員、帳號 | 專案與個人管理 | 固定可尋找入口；保留管理權限；初始化不要求無權限者執行管理操作 |
| AI／CSV／列印／全案匯出 | 輔助工具 | AI 放在問題脈絡，匯出表達範圍，列印保留正式格式；不與主要業務動作爭同等權重 |

### 視覺改善規則

- 頁首：案件／期別等脈絡 → 當前狀態及責任方 → 本頁工作說明；避免同時放多段口號與同義導覽。
- 清單列：事項名稱為第一層；期限、責任、版次為第二層；金額或判定只在有助判斷時顯示。狀態不能只靠顏色。
- 詳情：先內容和證據，再操作；主要動作標明業務結果，刪除及匯出放次要位置。
- 表單：把本次必填、補充資訊、唯讀來源分清楚；錯誤放在可修正的位置，頁首摘要可保留。
- 回饋：區分「已存檔」「已提送」「已交監造」「僅產生草稿」；失敗保留輸入，部分成功說明已完成哪一部分。
- 沿用現有設計 token、圖示和共用元件。先在送審／日誌驗證，再擴散；沒有第二個使用點就不抽象化。

## 6. 實作階段與每階段完成條件

工量為範圍判斷，非工期承諾。中等代表數個頁面與一條流程；大代表跨角色或多種例外，應拆成小 PR。

| 階段 | 交付 | 對應問題 | 工量／依賴 | 結束條件 |
| --- | --- | --- | --- | --- |
| 0：設計定案 | 現況核對、三角色任務圖、桌機網頁版入口草圖、產品待決清單 | U04、整體 | 小；先做 | 使用者看得懂改前／改後，明確選定下一階段；不改程式 |
| 1：操作可信度 | 明選驗收結果、建立失敗保留輸入、AI 承諾及角色文案修正 | U01–03、U13 | 中；不必等全面 IA 重排 | 成功／失敗／取消各有可核對結果；不改狀態機 |
| 2：入口與工作接續 | 導覽規則、初始化與待辦並存、功能尋找／AI 分工 | U04、U05、U12；U11 部分 | 中；依賴階段 0 入口定案 | 三角色桌機網頁版功能可達，無標單可做的工作不被整頁取代 |
| 3：廠商流程 | 先送審附件與補正，再品質編輯保護，最後日誌層級 | U06、U07、U14 | 大；拆 3A／3B／3C | 三條工作逐一走通，每次只交付一條，不把三者塞一個 PR |
| 4：監造流程 | 送審審查順序與完成回饋；驗證後延伸疑義／查驗 | U08、U03 呈現 | 中；沿用階段 1、2 | 可在保留證據與原佇列脈絡下完成受理、退回、審定 |
| 5：機關流程 | 金流保存狀態、變更決策摘要、驗收當前階段 | U09、U10 | 大；拆 5A／5B／5C | 範圍與結果清楚，無暗示付款已執行、無錯誤核定權限 |
| 6：整體驗收 | 桌機返回／深連結補齊、文案與真人任務驗收 | U11、U13、U14 | 中；主要流程完成後 | 三角色能完成指定任務，已知限制及待決事項明示 |

**最值得先讓 Claude Code 做的是階段 1。** 如果要先確認整體方向，就先貼階段 0；不要把整份報告貼上後要求它一次完成全部問題。

## 7. 不應混入這次前端整理的決策

| 候選能力 | 為何不直接實作 | 目前可先做 |
| --- | --- | --- |
| 送審草稿／附件齊全後才正式送出 | 改變正式提送時點、狀態轉移及對方可見性 | 提送與附件各自清楚標示，成功後接續上傳 |
| 真正背景 AI 工作、跨頁恢復結果 | 需要結果來源、持久化與生命週期，不只是 UI loading | 修正文案，揭露目前保存範圍 |
| 金流多欄原子儲存 | 需檢查現有 API／DB 保證，不能由多次前端寫入冒充 | 現有逐欄寫入加清楚狀態與失敗恢復 |
| 手機完成估驗／金流／變更表格操作 | 與目前手機唯讀設計界線相關；行動裝置優化本輪延後 | 保留現有功能及限制，不新增手機接續流程 |
| 完整「今天已完成」／跨渠道相同提醒 | 需要可靠完成事件與前後端來源對齊 | 明示資料涵蓋，保留活動紀錄入口 |
| 離線、跨裝置草稿同步、個人首頁客製 | 需要儲存、安全清理、衝突策略，且尚無使用研究證明必要 | 本頁離開防護及角色合理預設 |

以上不能在 UIUX 名義下直接改角色、RLS、RPC、契約來源權威、AI 人工邊界或正式資料。

## 8. 驗收方式：看能否做完工作

以下是建議測試腳本與門檻，尚未量測達成。先以同一批資料記錄改前基準，再走改後版本；不要只比較截圖是否漂亮。

| 測試 | 給使用者的任務，不告訴他按哪個按鈕 | 成功條件 |
| --- | --- | --- |
| C1 廠商／桌機網頁 | 填今天的施作量、加照片，告訴我哪些已保存 | 保存與草稿可分辨，附件失敗可重試，主要動作可觸及 |
| C2 廠商／品質 | 自檢填到一半，查看查驗紀錄，再繼續；完成後申請查驗 | 未靜默丟資料；沿用正確工項與檢查表版本；看懂等待監造 |
| C3 廠商／送審 | 提送一件資料，遇到失敗重試，再處理一件退回補正 | 失敗不重填；附件狀態清楚；補正原因與版次可追溯 |
| S1 監造／桌機 | 找一件補正再送，對照資料後留下意見，退回其中一件 | 能找到補正及現有證據；退回與駁回可區分；返回原工作位置 |
| S2 監造／桌機網頁 | 開待查驗項，判不合格，再查看產生的缺失 | 明確判定與原因；缺失建立失敗時不假稱全成功 |
| S3 監造／桌機 | 找指定估驗期，核對來源數量與佐證 | 正確期別，不回退到其他期；維持監造核定權責 |
| O1 機關／桌機 | 找一件待核定變更，說明影響後作決定 | 能指出事由、已知影響及缺資料處；正確的機關核定動作 |
| O2 機關／桌機 | 登錄某期金流，處理一次儲存失敗 | 不混淆全案統計；知道正式值與未保存值；可重試 |
| O3 機關／驗收 | 只填日期先登錄，再補選結果 | 第一次必須被提示選結果；第二次記錄與選擇一致 |
| X1 三角色／新案 | 標單未匯入，但已有一筆合法待辦，找出並處理 | 初始化不遮掉可做事項；不要求一般成員越權設定 |
| X2 三角色／導航 | 從有篩選的提醒進單據再返回；重整；改用失效連結 | 保留合理脈絡，失效訊息可理解，不靜默換單 |
| X3 三角色／手機至桌機（延後，本輪不驗） | 在手機找到需桌機處理的指定期別／單據 | 看懂限制且保留識別與連結，不承諾未實作的跨裝置自動同步 |

每次記錄：能否獨立完成、第一次點擊、繞路／求助、是否知道已保存與下一責任方、操作錯誤、用時。時間與點擊數先量基準，再訂有依據的目標；不要預先承諾「三步完成所有工作」。

建議每角色找 2–3 位實際使用者做探索性測試，不作統計代表性宣稱。即使自動化測試全綠，若使用者不能說明「我剛剛做了什麼、現在輪到誰」，仍屬流程驗收未通過。

技術驗證沿用 DEVELOPMENT：文件、lint、單元測試、build，加上本階段的 Demo E2E；涉及後端失敗情境應補失敗回應測試及可用的真後端驗證。不要為純文件報告重跑整套程式測試。

## 2. 三角色各兩條主要任務：目前 → 建議

標記：⛔ 中斷（流程停住或結果誤判）、🔁 重找（要自己再找一次位置）、❓ 資料不足（畫面沒有可判斷的資料，或資料模型沒有）。所有頁面與動作名稱皆為現行字串。

### C-A 廠商：每日現場填報（施工日誌）

**目前**

1. 今日待辦「現在輪到我」→「今天還沒有日誌紀錄」→ `/site-log`（不帶日期，預設今天）。
2. 本日日誌卡：日期／天氣／工作摘要 → 可按「複製昨日」→ 工項數量表。
3. 「公定格式欄位」預設展開，表單變長，「存檔」鈕在最底（桌機不貼底）。🔁
4. 按「存檔」→「已存檔 ✓」。存檔前畫面沒有「未存檔」標記，只有離頁時的內部防護。❓
5. 要傳照片：往下捲到另一張「現場照片」卡；未存檔時提示「請先存檔本日日誌，才能上傳照片」。🔁
6. 照片上傳結果訊息在照片卡，日誌存檔訊息在存檔列，兩處分開。

**建議**（同一頁，不新增精靈）

1. 待辦帶 `?d=YYYY-MM-DD`，進頁即該日；卡頭固定顯示「日期 ＋ 保存狀態：未存檔／存檔中／已存檔 HH:MM」。
2. 順序改為：本日施作數量 → 現場照片（緊接數量表，仍需先存檔才能上傳，但提示就在該處）→ 公定欄位預設收合，摘要列顯示「已填 n 列」或「尚有必填未填」→ 存檔列桌機也貼底。
3. 存檔與照片上傳結果各自回饋，但都顯示在貼底列同一位置，措辭區分「已存檔」「照片 3 張已上傳，1 張失敗可重試」。
4. 離開前有未存檔輸入：沿用共用確認對話框「離開將遺失未存檔內容」，取消可留下繼續。

### C-B 廠商：送審與補正

**目前**

1. `/submittals` → 頁首「提送送審」→ 表單（名稱／類別／提送日／期限／附件說明，placeholder 說「文件另以公文/雲端連結提送」）→「提送」。
2. 不論成功或失敗表單都收起。⛔ 失敗時輸入消失。
3. 成功後新件在清單頂，但右欄仍是原本選中的那筆，要自己點新件。🔁
4. 詳情附件區顯示「尚未上傳文件本體」→「上傳文件」→ 動作列只剩「待監造審定」字樣。
5. 補正：今日待辦「SUB-003 … 退回補正」→ `/submittals?submittal=…` → 詳情看「審查意見」（退回原因）→ 附件區「更換文件」與動作列「修正再送」分在兩區，沒有先後提示。🔁
6. 「修正再送」對話框填補正說明 → Rev.+1、狀態回「已提送」；補正說明併入附件說明字串，歷次補正與退回不能分列對照。❓

**建議**（沿用建立即「已提送」，不加草稿狀態）

1. 提送成功：表單收起、自動選取新件、詳情頂端顯示「提送紀錄已建立 · 尚未附文件」；失敗：表單保留、列出可重試錯誤。
2. 附件區改成一個「文件與提送方式」區：上傳／更換文件、附件說明、外部提送說明並列，下一步文字直接寫在此區（「上傳後由監造受理」）。
3. 退回補正件：詳情頂端出現「本件被退回：原因 …」「本次要做：① 更換文件 ② 修正再送」兩步並排，順序清楚。
4. 再送成功：頂端改為「Rev.2 已再送，待監造受理」，並保留「返回今日待辦」。歷次補正說明仍存在附件說明內；要分列對照需另存版次紀錄，屬 §5.1 待決。

### S-A 監造：送審審查

**目前**

1. 今日待辦「SUB-002 … 待監造審定」→ `/submittals?submittal=…`，頁首有「返回今日待辦」。
2. 詳情：球權章＋類別 → 編號／名稱 → 六格 MetaGrid → 附件 → 審查意見（上一輪的）→ 動作列。
3. 動作列同時出現「受理審核」「退回補正」「AI 審查助手」「AI 讀文件審查」；受理後換成「核准」「核備」「退回補正」「駁回」。兩階段只靠按鈕出現與否表達。
4. 補正再送件：只看得到 Rev.2 與併在附件說明裡的「補正(Rev.2):…」，看不到「上次為何退回 vs 這次改了什麼」的對照。❓
5. AI 結果在頁面 state；離頁即失，文案卻說可回來看。⛔
6. 審定後：詳情留在原件、列離開「待我處理」篩選、可按「返回今日待辦」。這段已可用。

**建議**（詳情重排，動作與狀態機不變；見 §4.1 草圖）

1. 頂端「輪到我做什麼」摘要條：階段（待受理／待審定）、版次、本次補正說明、上次退回原因；資料沒有就寫「首次提送」「無退回紀錄」。
2. 附件與 AI 助手放同一區，AI 兩顆各一句說明資料範圍（「依契約規範與工項」「讀已上傳文件本體」）與「結果只保留在本頁」。
3. 審查意見與決定放同一區並分兩段：「受理」一段（受理審核／退回補正），「審定」一段（核准／核備／退回補正／駁回），駁回沿用 danger 並加註「終局」。
4. 完成後摘要條改為「已核准 · 交廠商」，提供「返回今日待辦」與「下一件待審（n）」，後者由人點，不自動換單。

### S-B 監造：查驗判定

**目前**

1. 今日待辦「查驗 …」→ `/quality?inspection=…`。
2. 品質頁：頁首 →「現在要處理」佇列 → 五顆分段 chips → 查驗分段清單／詳情（含「附自主檢查表」）。
3. 詳情「判定合格」／「判定不合格」→ 不合格必填原因 → 寫入 → 訊息「已開立缺失」＋「查看缺失」。
4. 「查看缺失」切到缺失分段；從佇列點一筆會以 `queueTick` 重掛分段，分段內未送出的表單與篩選重置。🔁
5. 缺失開立失敗時錯誤橫幅會如實說「判定已記錄，但缺失開立失敗」。這段已可用。

**建議**

1. 保留流程與判定對話框。判定成功訊息直接帶缺失深連結 `?defect=…`，切段時只換分段與參數，不重掛整段（U07 的同一修法）。
2. 詳情頂端一行「申請日／申請人／檢附自檢表 Rev.」，缺自檢表時維持「未檢附自主檢查表」。
3. 完成後保留「返回今日待辦」。其餘分段編輯保護歸階段 3B。

### O-A 機關：變更設計核定

**目前**

1. 今日待辦「CO-002 … 待機關核定」→ `/change-orders?co=…`。
2. 頁面最上方先是四張全案 Stat 卡（原契約金額／累計追加／累計減帳／變更後金額），再是清單與詳情。🔁 待核定件被推到下方。
3. 詳情：狀態＋淨額 → 編號／事由 → MetaGrid（日期／狀態／明細筆數／理由）→ 追加減帳明細表 → 核准／駁回。
4. 沒有監造受理意見、沒有附件、沒有工期影響，因為資料模型本來沒有這些欄位。❓（不可捏造）
5. 「核准」「駁回」直接寫入，沒有確認框；核准後明細凍結，撤銷入口待決（ROADMAP）。⛔ 判準第 5 條把核定列為需確認的不可逆動作。

**建議**（見 §4.3 草圖）

1. 四張全案 Stat 卡移到清單下方或收成一行「變更後契約金額 7.23 億（＋0.2%）」，讓待核定件先出現。
2. 詳情順序：「待你核定」摘要（事由、理由、提出日、淨額、核准後契約金額將為 X）→ 明細與差異 → 「本系統未登錄」區（工期影響／監造意見／附件三項明寫未提供）→ 核准／駁回。
3. 核准與駁回各加共用確認框，內容指向單據：「核准 CO-002，淨額 ＋1,764,000，核准後契約金額 …」；駁回同樣確認。DB 無駁回原因欄，不新增。

### O-B 機關：驗收登錄

**目前**

1. 今日待辦「初驗期限將至」→ `/acceptance`，不帶階段。🔁
2. 頁首副標是角色提示句，專案名稱被取代。❓（U13）
3. 法定期限提醒卡 → 驗收流程時間軸 → 找到第一個未完成階段（其他階段顯示「需先完成前一階段」）。
4. 填實際辦理日／結果（第一項為空白）／備註 →「登錄」；未選結果送出即合格。⛔
5. 登錄後該列變已完成，可「修改」；沒有「下一階段是什麼」的接續句。

### 3.3 D-015 與現況衝突的處理

現況衝突點只有一個：`PageTabs` 常駐在內容區，而 D-015 寫「內容區不重複子頁導覽」。但 D-015 同時要求「桌面側欄可收合」，收合後側欄只剩圖示，此時內容區若也沒有子頁，1024–1279 px 的桌機瀏覽器就沒有子頁入口（`a11y.spec.js` 在 1024 px 斷言側欄收成 <120 px）。所以「不重複」應解讀為「側欄已顯示子頁時不重複」，方案 B 正是這個解讀。本階段不改 DECISIONS；若採 B，實作包（2a）只在 Apple 規範 §0 補註記，並在 CURRENT §6.1 記錄行為。

## 任務與執行順序

請閱讀 `AGENTS.md`、`DEVELOPMENT.md`、`CURRENT.md`、`docs/DECISIONS.md` 及 `docs/reviews/2026-09-20-contractor-acceptance-report.md`，針對既有程式修正，完成實作與驗收，不要只再寫計畫。

使用者下週要交施工廠商使用。順序固定：**施工廠商 > 為廠商流程必要的監造操作 > 機關擴充；桌面網頁 > 手機**。產品只聚焦三件事：

1. 照片／既有資料 → AI 填好工程文件 → 人審核、簽署、送出。
2. 契約 AI 擷取 → 可追溯的要求與期限 → 告訴各角色何時要做什麼。
3. 監造確認的完成量 → 自動更新可估驗量 → 估驗、請款。

沿用使用者指定的工作模型分工：簡單且低風險 `opus5.2`；複雜或高風險 `fable5.1`。純文案、定案後的樣式與文件整理屬前者；AI 資料模型、欄位 mapping、權限、簽署、數量單位、計價、migration、整合與驗收屬後者。這些是使用者給的名稱，先確認執行環境是否提供；不能虛構模型 ID 或宣稱已切換。不可因此更換產品呼叫的 AI 模型。無法使用時明示限制，不擅自改名代替。

省 token：只讀相關模組；沿用既有測試；每包改完跑必要驗證；不要重造平台、泛用表單設計器或多代理編排。先做下列 A–D，再處理 E 的完整收尾。

## A. 廠商角色與三個主入口

**已知問題：** `src/lib/navConfig.js` 未區分監造作業的導覽角色；`src/pages/web/Site.jsx` 手動列出監造日誌／查驗表單，文件清單也混列三方文件；`navConfig.test.js` 的廠商斷言包含這兩項。

- 廠商主選單、分頁、現場作業卡片、新增選項及「我的文件」不能出現監造日誌／監造查驗表單作為廠商工作。不能只藏一處，也不能只改名稱。
- 廠商保留：施工日誌、自主檢查、照片上傳、查驗申請、補正、查看查驗結果與可估驗量。
- 監造保留其日誌、查驗、收件及確認量操作，確保廠商送出的東西有人能處理。
- **移除監造作業入口，不可誤刪廠商應收的查驗結果或計價依據。** 在「查驗結果／估驗依據」提供唯讀內容；必要既有深連結仍可依原權限唯讀收件。不要讓廠商看到監造起稿入口或草稿工作清單。
- 導覽只突出「AI 文件」「契約期程」「估驗請款」三個群組；今日待辦作為首頁，專案／成員／原始文件作次入口。查驗、缺失補正、停留點等必要步驟嵌回對應主流程。
- 先收起獨立工安工作區、試體管理、S 曲線、月報、跨案分析等非此次主要操作；保留文件所需欄位、必要提醒及歷史資料。不要為瘦身刪掉請款必經查驗、契約證據、原始照片或簽署紀錄。
- 保持 `contractor/supervisor/owner` 三角色，導覽與授權分開處理，RLS／RPC 不因 UI 調整被放寬；必要角色用例更新測試。

**驗收：** 一般廠商帳號含專案 admin 情境，首頁／側欄／頁籤／新增選單沒有監造作業入口；仍能提送查驗、收到結果及開啟計價證據；不能簽署監造文件。測試不得繼續斷言舊的混列行為。

## B. 真正的照片辨識與 AI 填表

**已知問題：** `_shared/sitePhotoVision.ts` 用 `has_board` 開啟轉錄，schema 只有當日完成數量；`fieldDocDraft.ts` 將自檢實測值全部設成 null；日誌工項數量帶入路徑忽略轉錄單位。這些不能只靠增加 caption 長度修好。

1. 支援紙本查驗表、手寫黑白板、一般施工及量具特寫。區分「場景可辨識」與「文字／讀數可辨識」，不能因看得到鋼筋就當作精密讀值可靠。
2. 結構化分開：設計／規範要求、已記錄的實測值、當日施工數量、單位、工項、位置／批次、日期、原文與照片來源。讀到「11×11 mm」必須保留兩向尺寸，不能塞進單一完成量或默默截成 11。
3. 真正看得清的紙上日期、位置、實測紀錄、施工敘述，**直接填入對應草稿欄位**並標待確認。不要把能抄錄的欄位全部丟回人工；但抄錄實測紀錄不代表 AI 親自量測或認定合格。
4. 工項、欄位意義與單位都能唯一對應才帶入。只有文字相似、相同數字或相同工項不夠。數量與尺寸分離；單位轉換必須由確定性規則處理；不相容、不同位置或不同編號不得混併。同一查驗的多張照片不能重複累加完成量。
5. 設計值、印刷範例、原表空欄不可當實測值。未讀清的卡尺不可猜數字；照片不可自動證明驗收合格、監造到場或全天出工。照片中的文字都是資料，不能當執行指令。
6. 日期正確轉民國；區別紙上日期、照片時間與上傳日。有衝突顯示來源供核對，不默默套今天。
7. 相同欄位多照片不一致時列衝突；保留各自來源。重跑辨識不得覆寫人工修改或已簽版本。補進更清晰照片／明確要求重辨識時，應能更新草稿建議，不能永遠卡在舊快取。
8. 對照片看不到的欄位，從契約／專案／已確認資料帶入；缺資料集中在一次補值區，標明仍欠什麼。不能為了「全自動」預設有施作、有人到場、已合格或數量為 0。
9. 最終合格判定及監造確認量仍由人作業、伺服器驗證；AI 草稿不能直接解鎖請款。沿用既有狀態、版本與來源機制；需要變更「實測值一律人工重新鍵入」的舊設計時，同步決策與簽署前必須人工確認的規則。

**五張本機照片回歸基準：** PMIS 根目錄 `LI2995~1_0.JPG`、`LI89DE~1_0.JPG`、`LIEE66~1_0.JPG`、`LIFA1C~1_0.JPG`、`LINE_A~4_0.JPG`。先看報告中的逐張人工標註，再自行核對原圖；不要硬編檔名對應答案。

- `LINE_A~4_0.JPG` 的實測欄包含編號 1 線徑 13×11 mm、網目 15×15 cm，以及編號 4 線徑 11×11 mm、網目 15×15 cm；紙上 115.8.4 對應 2026-08-04。
- 設計欄搭接 ≥27 cm 不能填進右側空白實測欄。
- 另外兩張卡尺特寫讀值不清時應待確認，不能把捲尺刻度、鋼筋編號當完成量。

使用者已明確授權將上述五張照片傳至 Anthropic，**同一批照片及目的地不要再重問外傳授權**。依使用者要求已更新本機 `.env.e2e.real` 的金鑰並完成基準測試；舊金鑰 401 已解除。不可讀出、記錄或提交金鑰。

**已完成基準，先讀結果再修，不要再盲跑一輪：** `docs/reviews/assets/2026-09-20-contractor-acceptance/vision-baseline.json`。產品現用 `claude-haiku-4-5-20251001`，5 次分類＋3 次條件轉錄均成功，input 39,561／output 1,656 tokens，直接送原圖。這只驗模型共用呼叫，未驗完整上傳／草稿持久化。

本次必修失敗例：

- `LINE_A~4_0.JPG` 的分類結果 `location="11F"`，caption 還生成不存在的公司名稱、樓層與配置；轉錄的 location 卻空白。不得讓沒有原文證據的分類位置直接落進文件分組。
- `LI2995~1_0.JPG` 的 visible_progress 寫「綁紮完成」，違反現有禁止推定完成的 prompt；只加一句禁止敘述不夠，需證據檢核及不確定時留空。
- `LIFA1C~1_0.JPG` 把紙上資料混讀成 D13／D16／D29、間距 13／15 cm，未正確承接兩向實測尺寸。
- 三張紙表 **都有 has_board=true 且日期正確**，所以不能將問題歸因為單純未偵測到紙表。三張轉錄皆只有日期、其餘空白及 items=[]。沒有完成量的照片，items=[] 可以是正確結果；另提供結構化實測欄，不能把尺寸硬塞進數量。
- 卡尺特寫沒有猜測精密讀值，這項行為保留；`LIEE66~1_0.JPG` 額外生成的「木樁樁頂面」描述須避免。

修改後以同一組圖片與基準逐欄比較期望／實際／缺漏／誤填／需人補；記錄模型、prompt 版本、延遲與 token。不得將原圖基準與前端壓縮圖的結果混為同一條件，另驗上傳實際送圖流程。優先針對紙表區域與困難圖片做第二階段辨識和來源核對，不全面換最貴模型。5 張只能作回歸集，至少補設計／實測相反、單位衝突、模糊、不同工項與同場重拍等負例。真實模型與 stub 結果分開報告。

**驗收：** 日期、文字與清楚的已記錄實測值能出現在表單格子；點欄位能回看證據。回歸集不得把設計值當實測、尺寸當施工量、空白當合格；所有錯填逐項修正或列待確認，不以通用 caption 冒充完成填表。

## C. 真實表單 mapping，直接在紙本版面編輯

目前廠商日誌用 `DailyLogFields`，唯讀／列印才用 `SiteLogOfficialSheet`；自主檢查也有不同的 Fields 與 Sheet。請統一欄位定義與資料 mapping，**廠商預設就看到能編輯的真實表單**，不是另一個精簡表填完才切紙本預覽。

已準備的原始範本在 `docs/reviews/assets/2026-09-20-contractor-acceptance/`：

| 本輪順序 | 原檔 | 官方來源 |
|---|---|---|
| 1 施工日誌 | `pcc-daily-log-1080430.pdf` | [工程會 108.04.30 附表四](https://www.pcc.gov.tw/content/index?eid=5886&lang=1&type=C)，4 頁含附表 |
| 2 自主檢查 | `taipei-rebar-self-check-example.odt` | [臺北市鋼筋自主檢查格式參考範例](https://gpis.taipei/DL_File.aspx?ID=12919&tb_name=km_quality_download&tb_id=24) |
| 3 必要監造查驗 | `taipei-rebar-inspection-example.odt` | [臺北市鋼筋施工抽查紀錄表](https://gpis.taipei/DL_File.aspx?ID=12920&tb_name=km_quality_download&tb_id=24) |
| 4 監造日誌 | `pcc-supervisor-log-1080430.pdf` | 同上工程會頁面的附表五「公共工程監造報表」；每日報表，非監造月報 |

工程會附件直接 URL 存在同資料夾 `pcc-sources.json`。採用前讀原檔完整內容；台北市 ODT 包含批註、良好與不良填寫示例，**不得把示例數值、不良範例的錯誤判定或假公司名載入真實專案**。版面參考與工程技術標準分離：標準只能取本案核定規範／圖說／範本，缺少則待補。

每份先完成 mapping 清單：原表欄名 → 儲存欄位 → 來源／計算 → 可編角色 → 必填／不適用條件 → PDF 位置。要涵蓋表頭、各節、續頁、附表與簽章，不可只做大致相似的表格外框。

具體要求：

- 白底、清楚表格線、原表欄名與章節；格內可編輯，AI 已帶入值已出現在格子裡。來源與待確認提示在畫面上輕量呈現，點選可看原照片／原文。
- 專案資料自動帶入；累計量、工期、進度依既有確定性規則，禁止 AI 編數字。無本案依據的原表欄位列待補或由人註明不適用。
- 桌面左側以表單為主，照片／待補提示可放右側；不要同時鋪滿多組工具卡。常用動作：上傳照片、審核待補、儲存、簽署送出、下載 PDF。
- 保留表格編輯的鍵盤操作、焦點與錯誤定位；手機先確保上傳、檢視與審核能用，不展開另一套重設計。
- 範本名稱與來源誠實：標為「參考工程會／臺北市格式」，保存版本及來源；不得未經核定就聲稱機關正式認可。
- 簽署版本必須保存當時欄位／範本語意，後續改範本不能悄悄改變舊文件內容或判定。

## D. PDF 交付

- 提供真正的「下載 PDF」；目前 `PrintToolbar` 呼叫 `window.print()` 只能算列印／另存功能，不能當直接下載已完成。
- 共用同一套表單資料與欄位 mapping；草稿有未簽署標示，正式文件取不可變的已簽版本與其簽署資訊，不能取後來未簽草稿。
- A4、多頁自動換頁、長表重複表頭、中文可正常顯示；簽章和表格不截斷；照片附件有說明及對應欄位。不要把整份文件只做成低解析度截圖。
- 不新增未核准付費服務。沿用或選最小可維護方案，實際下載檔案後渲染核對；記錄一般、長表、多照片與改版後重印案例。失敗時清楚提示，不下載空白或半份 PDF。

## E. 三項核心的整條流程驗收

不要重做已有的確認量分配引擎。查閱 `confirmed_quantity_enforcement` 等現有 migration 與 `e2e-real`，把必要缺口修到通過：

1. 廠商上傳照片 → 日誌及對應自檢草稿 → 核對待確認欄位、補值 → 儲存、重登仍在 → 簽署 → 提送 → 監造收件／退回 → 廠商修正再送。
2. 廠商自檢／查驗申請 → 監造表單 → 監造簽署確認本次數量 → 廠商看到來源、已計價／占用及剩餘可用量 → 符合截止日的草稿估驗自動更新；未建期先累積，已送審／核定期不自動改寫。
3. 未查驗、AI 草稿、自檢合格皆不能直接解鎖請款。驗部分通過、不同工項／位置／批次／單位、重複照片、重播、併發、多期重複占用、撤銷減量與截止日；UI、REST、RPC、Edge、匯入皆不能繞過。
4. 契約上傳 → 擷取重點 → 引用原文 → 建立履約義務 → 正確角色在到期前看到下一步與入口。缺基準日／頻率時顯示待補；逾期、改期、取消、已完成與保固停止條件有測試。照片日期不能改變契約期限。
5. 三角色完整簽收及估驗／請款鏈以隔離真後端驗證；Demo 與 stub 只證明流程。未測正式部署就寫未測，不能引用舊報告宣稱本次已通過。

既有決策維持：不重新加入 MFA；總價／間接費暫 `cap=0`，不可偷偷解鎖；未核准付費 OCR，不因本任務新增。若這些限制阻擋試用專案，具體列出缺什麼與影響，不承諾完整自動化。舊資料、簽章、確認量與計價稽核不得刪除。

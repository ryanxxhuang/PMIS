## 1. 管理摘要

**產品已有可繼續發展的工程基礎；下一階段應集中把「契約文件 → 履約要求 → 三方待辦 → 佐證與追溯」做成可信任的完整流程，再擴充功能。**

目前值得保留的資產是：公共工程領域模型、PCCES 工項與估驗鏈、三方權限與狀態轉移防護、文件原文定位、AI 功能閘門，以及相當完整的自動化回歸測試。沒有證據支持推倒重寫，或先抽象成跨政府業務平台。

阻礙使用價值的主要因素不是頁面數量，而是以下四點：

1. **可信度**：履約時程會把未通過逐字核對的 AI 自動確認內容標成「系統核對無誤」。循環義務目前只推下次日期，不能完整反映每一期漏交與準時率。
2. **流程一致性**：機關自己的契約期限不進今日待辦；正式且已匯標單的專案，成員管理缺少一般介面入口。深連結能開頁，不代表使用者找得到。
3. **資料與營運完整性**：文件頁面讀取有單次 1,000 列上限風險，專案刪除未串接 Storage 清理，AI 配額欄位尚未形成實際限額控制。
4. **驗證方法**：測試綠燈證明受測行為穩定，尚不能證明真實契約抽取完整、手機現場可用、資料可還原，或使用者願意持續使用。

**成熟度判斷：可在明確揭露限制、有人陪同的條件下做小範圍試點；目前證據不足以宣稱已適合無人陪同、大規模正式導入。** 這是依證據覆蓋程度做的產品判斷，不是資安或法遵認證。

| 面向 | 判斷 | 主要依據 | 下一個里程碑 |
|---|---|---|---|
| 產品定位 | 聚焦方向合理，價值尚待真案量測 | 文件與履約鏈已成形，四入口集中於此 | 用真實契約證明找條文與追期限省時 |
| 功能與使用流程 | 有功能，關鍵路徑有斷點 | 成員入口、機關待辦、循環義務 | 三方各自完成一條可重複工作鏈 |
| 權限與資料防護 | 有明確防線與回歸證據 | routeRegistry、RLS、Guard、927 pgTAP 斷言 | 補目前版本的真後端整合驗收 |
| AI 品質與透明度 | 機制具備，語意與完整性需補強 | sourceVerify、D-019、誤導標示、缺評測基線 | 可信標示、漏項評測、版本退步檢測 |
| 前端與工程維護 | 基礎穩定，局部負擔偏大 | 767 單元測試、42 Demo E2E、建置成功 | 修高價值流程，按實測處理效能 |
| 營運與復原 | 有監控元件，營運結果尚未完整驗證 | Sentry、cron、版本與備份待核 | 實際還原、提醒送達、費用上限驗收 |
| 商業導入 | 證據不足 | 本次沒有營收、採用與客戶訪談資料 | 一個清楚使用情境、一套試點成功條件 |

不給單一總分：尚未重測的正式環境與未量測的客戶價值，不能與已通過的程式測試平均成看似精確的分數。

## 4. 優先處理的發現

優先序定義：**P0** 為已確認需立即停止或緩解的重大事故；本次沒有足夠證據宣告 P0。**P1** 為下一批真案導入前應完成或明示限制的項目；**P2** 為依使用頻率與量測結果安排。分級不代表漏洞利用評分。

### H-01｜P1：自動確認被誤標為「系統核對無誤」

**證據強度：程式確認。** `src/pages/web/Requirements.jsx:127` 沒有讀取 `triage_doubts`；同檔 `:421` 只看 `reviewed_by` 是否存在，沒有人工 reviewer 就顯示「系統核對無誤・自動確認」。但 D-019／最新 migration 明確允許帶疑慮資料進 `approved`。相鄰的 `RequirementsReview.jsx:121`、`:688` 已有區分疑慮的呈現。

**影響**：使用者在主要履約頁把「系統自動歸檔」理解為「系統已驗證正確」，破壞 D-019 依賴的透明揭露。

**建議**：保留 D-019 的全自動策略，補查詢欄位、依真實核對結果顯示狀態；缺少核對資料時顯示「未取得核對結果」，不要當作無疑慮。原文優先聲明須出現在主要詳情，而不只藏於錯誤回報表單。

**驗收**：人工確認、自動且無疑慮、自動且有疑慮、核對資料缺值四種情境，在履約與審核頁均不誤標；不改人工業務核定權。

### H-02｜P1：機關自己的契約期限不進今日待辦

**證據強度：合成案例實測。** `src/lib/todayTasks.js:33` 的 `OBLIGATION_ACTIONABLE_SIDES` 是 contractor／supervisor；`:126` 依它過濾。`20260825120000_obligation_ownership_completed_at.sql` 已讓三方按歸屬更新自己的義務。

對三角色各給同一個 2026-09-07 到期、狀態「待辦」、責任方為自己的義務：廠商 `mine=1`、監造 `mine=1`、**機關 `mine=0`**。但機關可以在 `/requirements` 處理自己的義務。

**建議**：把機關自有期限納入，待辦連結直達有操作權的那筆履約義務；同時確認 `/deadlines` 與 `/requirements` 的實際操作權是否一致。不要只把 owner 加入常數卻導向仍不能操作的頁。

**驗收**：三方自己的到期項均出現；別方項不混入；點擊可完成並更新清單；同一日期與責任方在網頁、Agent、提醒信的差異有明確規格。

### H-03｜P1：循環義務尚不是逐期履約管理

**證據強度：合成案例實測＋程式明示限制。** `src/lib/contractDue.js:31` 每月期限只計算下一個日期；`obligationTimeline.js:222` 明講循環逐期準時率尚無後端實例可算。

| 合成輸入：每月 5 日交報告，今天為 9 月 7 日 | 現有結果 | 產品意義 |
|---|---|---|
| 狀態仍是待辦 | 日期 10 月 5 日、排程中 | 看不到 9 月 5 日是否漏交 |
| 8 月 5 日曾標完成 | 仍已完成，`onTime=true` | 未形成 9 月新一期待辦 |

這不是日期加減寫錯，而是**「下次日期提醒」與「每一期都應履約」的資料責任不同**。把每月、每週、每日列出來，不等於逐期管理已完成。

**近期建議**：介面與報告明示目前能力；循環項及缺完成時間的歷史項不宜在未說明下混入精確準時率。是否改分母、顯示未知或拆出比率，須先定產品口徑。

**後續開發方向**：先針對試點最常用的一種頻率實作逐期記錄，保留 Requirement／規則為權威，期次保存到期日、狀態、完成時間與佐證。不是現在就造通用工作流引擎。

**驗收**：本期逾期不被下期日期覆蓋；本期完成不代表下期完成；每期佐證可追溯；月末、跨年、月底 29～31 日、基準日更正與重跑不重複產期有明確規則及測試。此項需決策、新 migration 與 pgTAP。

### H-04｜P1：大文件讀取可能漏掉第 1,001 頁以後

**證據強度：程式確認、上限情境推導；未在正式大文件實測。** `supabase/functions/extract-requirements/index.ts:236` 讀 `document_pages`，有排序但沒有 range／分頁；`supabase/config.toml:18` 設定 `max_rows=1000`。

**影響**：W13 的 AI 批次續跑只能處理已載入的頁面，不能補回一開始未讀到的頁。若 hosted 同樣上限，長合訂本可能只處理前段，卻被當成整理完成。

**建議**：穩定排序分頁、比對預期頁數與實際處理頁數；中途一頁失敗不得回報全份完成。Agent／提醒的 `collectOpenBallItems`（`agentTools.ts:502`）也有未分頁列表查詢，應列同類檢查範圍。

**驗收**：999／1,000／1,001 頁，以及跨頁失敗、重試與續跑案例；第 1,001 頁有獨有條款時能被處理並保留正確來源。頁數完整與條款沒有漏抽必須分開衡量。

### H-05｜P1：成員管理與工作頁缺少穩定可發現入口

**證據強度：導覽與條件渲染確認。** `navConfig.js:14` 只呈現四個工作入口；五組工作面 hidden。`Dashboard.jsx:268` 在已匯標單的正式專案不渲染初始化卡，而成員連結在該卡內。既有 E2E 多使用 `gotoHash`，可驗證頁面可用，無法證明使用者找得到。

**建議**：先恢復低負擔、持續必要的「專案成員」入口；其餘依真案工作鏈逐項復出。四入口是已核准的精修策略，不應在健檢中自行恢復所有工作面。

**驗收**：三方從首頁只靠可見控制即可到達其本次工作頁；正式模式仍能管理成員；首次啟動流程不依賴已有待辦才能找到建立入口。加入點擊路徑 E2E。

### H-06｜P1：有 AI 計量，尚無產品層費用上限

**證據強度：程式確認；供應商後台額度未驗證。** `20260728000100_ai_platform.sql:105` 明示 `ai_monthly_token_quota` 只留欄位；現有 `ai_feature_allowed` 與 `_shared/aiGate.ts` 做功能／方案授權和事後記帳，沒有以配額預留來限制模型費用。

**建議**：先定義每專案／期間、平台總額與單次文件限制；警告和硬停用兩種門檻分清楚。若宣稱硬上限，需在請求進場時原子預留或限制並行，成功／失敗後結算與釋放，不能只查歷史用量總和，否則同時請求仍會穿透。保留既有「記帳失敗不破壞已完成回應」決策。

**驗收**：並行請求、重試、續跑、timeout 與記帳失敗均不導致無限花費；管理者能看已用、預留與可用額度；使用者知道何時恢復及可採取的下一步。供應商平台額度是另一層保護，需單獨確認。

### H-07｜P1：專案刪除未形成 DB＋檔案完整清理

**證據強度：程式確認；正式孤兒數未重測。** `src/store/slices/projects.js:285` 只呼叫 `delete_project`；其 baseline `:1006` 刪 projects row，沒有 Storage API 清理流程。

**影響**：專案資料列被刪與實體照片／文件被清掉，不是同一件事。過去孤兒數不能直接作為這次清理清單。

**建議**：刪除前保存授權範圍內的檔案清單；設計可重試、可追蹤的 DB／Storage 清理流程。兩個系統不能假裝單一交易：DB 已刪而 Storage 失敗時應保留待清理狀態；也要處理刪案後原本權限已不存在的問題。經 API 清實體檔案，不直接刪 Storage metadata。官方明確區分 metadata 與物件：[Supabase Storage schema](https://supabase.com/docs/guides/storage/schema/design)。

**驗收**：含檔專案刪除、部分 Storage 失敗、重試、跨案路徑拒絕、活檔不可誤刪；清理完成前不得宣稱所有資料已清除。正式清理應另取得明確授權。

### H-08｜P1：刪除留痕不等於原始稽核紀錄保存

**證據強度：schema 與政策語意核對。** `20260811000200_project_deletion_records.sql:6` 明示專案刪除會 cascade 移除 audit_events、agent_actions、ai_usage_events；留存的新紀錄含操作者、時間與事件數，沒有保留每一筆原事件內容。

**影響**：可以證明「誰刪了專案」，不能因此證明「該案每次業務操作仍可追溯六個月」。同樣會失去部分按案 AI 使用歷史。這裡不做法律違規認定；需依實際採購契約、保存政策與資料刪除責任定案。

**建議與驗收**：明確區分刪除證明、原事件保存、停用／封存、復原與到期清除的承諾；以一個測試案驗證刪除後究竟能查到什麼。未決定保存責任前，不急著改 FK 或一律永久保存。

### H-09｜P1：可還原與提醒送達缺乏本次證據

**證據強度：實作存在，營運驗收未知。** `src/lib/sentry.js` 有錯誤監控，`supabase/cron.sql` 有每日提醒設定；未核對目前告警收件、排程 HTTP 結果與郵件送達。

資料庫備份本身**不包含 Storage 實體物件**，這是供應商文件已確認的範圍，不能再列成「不確定是否涵蓋」；尚未知的是你的專案是否另有物件備份。[Supabase 備份說明](https://supabase.com/docs/guides/platform/backups)

**驗收**：從一組可對齊的備份，在隔離環境恢復資料列、原始文件、照片與存取權；抽查原檔雜湊與業務鏈，記錄實際可容忍資料損失時間與恢復時間。提醒則驗證排程觸發、函式完成、寄信結果三層，故障時有人收到告警；不要把 cron 成功呼叫視為信已送達。

### H-10｜P2：效能與維護要靠量測安排

**證據強度：建置實測。** 主 bundle `index-*.js` 約 **923.54 kB／gzip 286.42 kB**；PDF、Mammoth、工項資料另有較大 chunks。頁面已採 lazy load；檔案大不等於每個使用者每次都下載全部。

現有 a11y 測試含 375／1024px、觸控抽查和鍵盤場景，但不等於 WCAG 全項驗收；`/requirements/review`、建案頁等仍需補關鍵流程覆蓋。無本次量測前，不填 Lighthouse 分數或聲稱已改善 Core Web Vitals。

## 5. 產品應如何取捨

### 5.1 先建立一條可證明價值的主流程

建議主張：**把散落在契約文件中的履約要求，整理成三方各自能執行、能回到原文、能留下證據的工作清單。**

這與目前四入口、文件版本、Requirement、obligation、期限計算及證據連結相符。它的優勢是假如做完整，就能把閱讀文件與實際履約接起來；單純多一個聊天入口則不足以證明差異。

最小成功體驗應是：上傳真實文件 → 知道處理到哪裡及是否完整 → 找到一個明確要求和原文 → 設定必要基準日 → 責任方看到待辦 → 提送佐證／完成 → 另一方可追溯。先完成這一圈，再談全套工程管理全面開放。

### 5.2 三方都應有可持續使用的理由

| 角色 | 首次價值 | 重複使用價值 | 建議優先接回的能力 |
|---|---|---|---|
| contractor | 知道契約要求做什麼、何時交 | 今日工作、提送與佐證紀錄 | 履約待辦 → 送審／照片／施工日誌 |
| supervisor | 找到要求、來源與廠商交付 | 查驗／複查與待審交接 | 送審／品質 → 缺失處理 → 既有監造報表 |
| owner | 看清責任、逾期與依據 | 自己的待辦、跨案異常與追溯 | 自有期限 → 活動紀錄／風險稽核 → 跨案總覽 |

角色仍只用 contractor、supervisor、owner。需要指定經辦人時，可先處理任務指派與通知，不能把現場／品管／工安變成新授權角色。

### 5.3 AI 下一步應優先補品質證據

現有來源核對能檢查「抽出的引用是否在文字裡」，不能證明「沒有漏掉重要條款」，也不能證明責任方、日期觸發與條款語意正確。這是下一階段比換模型更有價值的投資。

建立經允許使用且移除不必要敏感資料的契約案例集，涵蓋掃描件、表格、附件、補充條款、中文數字、民國年、跨頁引用與相互衝突條款。由領域人員建立可對照答案，分別量測來源定位、條款召回、責任方、期限規則、重複率和每份文件人工修正時間。程式／SQL 測試與模型品質評測各負不同責任。官方也建議 agent 評測結合結果、執行軌跡與合適的評分方式：[Anthropic 評測方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

模型或 prompt 更新前跑固定回歸集；重大漏項不可被平均分數掩蓋。D-019 不必先撤回，但自動整理、核對通過與人工確認須一直可分辨。

### 5.4 本階段不建議優先投入

- 泛政府跨領域平台、外掛框架、微服務化或通用流程 DSL。
- 全站再改一次品牌或視覺風格；先處理能否完成工作的阻礙。
- 一次恢復所有 hidden 功能，卻沒有真案使用與驗收人。
- 新增更多 agent／聊天模式，或讓 AI 代替人工做正式核定。
- 沒有續期資料就做精細履約預測，或沒有可信基線就宣稱節省百分比。
- 沒有實際付款與帳務責任需求就建完整訂閱平台；先把費用可控與使用量可對帳做穩。

## 7. 試點的成功條件與量測

建議先找少量真實專案，至少讓每一種角色都有實際操作者；初期可用操作記錄與簡單表格，不需先建分析平台。以下為**建議量測口徑，尚非目前成果或既有 KPI**。

| 要驗證的問題 | 量測方式 | 決策用途 |
|---|---|---|
| 第一次使用多久看到價值 | 上傳開始到使用者找到一條可執行、能開原文的要求；拆分等待與操作時間 | 找 onboarding 與解析瓶頸 |
| 抽取是否可用 | 人工標註必要條款中被正確抽出的比例；另記重大漏項、錯責任方與錯期限 | 決定是否可擴大文件類型 |
| 整理是否真的省時 | 同等難度文件的原工作方式與產品方式比較，包含核對與修正時間 | 避免只計生成速度而忽略返工 |
| 三方工作是否閉環 | 抽查有來源、責任方、到期／觸發、執行紀錄與必要佐證的工作比例 | 決定優先補哪個交接頁 |
| 是否持續使用 | 依各角色工作頻率看次週／後續週回訪與有意義動作；排除測試帳號 | 辨識角色價值不足或導入問題 |
| 成本是否可承擔 | 每成功整理一份文件、每活躍專案的模型與服務成本；重試也納入 | 訂合理額度與導入規模 |
| 可靠性是否夠 | 完整成功、部分成功、失敗可續跑、提醒送達與恢復演練結果分開記 | 設定可以對外承諾的服務範圍 |

先量一輪基線，再由使用者與試點方確認目標值。可立即要求的硬條件是：不能跨案越權、不能把處理不全說成完成、不能把有疑慮說成核對無誤；效率與回訪率則要依專案頻率比較，不能任填漂亮數字。

## 一、記錄什麼（四類日誌）

| 日誌 | 記錄對象 | 儲存位置 | 保留期 |
|---|---|---|---|
| **應用稽核事件** | 估驗、查驗、缺失、送審、變更、驗收等業務狀態轉移與其前後值；專案成員與角色變更 | `audit_events` | **不設自動清除，至少六個月** |
| **AI 代理行為** | 每個 AI 動作的角色、種類、目標、理由、佐證與人的覆核結果 | `agent_actions` | 同上 |
| **AI 用量事件** | 功能、使用者、專案、token、成本、狀態 | `ai_usage_events` | 同上 |
| **身分驗證事件** | 登入、登出、密碼變更等，含**來源 IP** 與時間 | `auth.audit_log_entries`（Supabase Auth 原生） | 同上 |

### 每筆稽核事件包含的欄位（對應一覽表的列舉項目）

| 一覽表要求 | 對應欄位 |
|---|---|
| 時間 | `occurred_at`（`timestamptz`，內部即 UTC，可對應 UTC／GMT） |
| 使用者身分識別 | `actor_user_id` ＋ 當下的 `actor_party_type` / `actor_project_role` / `actor_is_project_admin` 快照 |
| **IP 位址** | `actor_ip`（`inet`） |
| 事件類型 | `event_type` / `action` |
| 發生位置 | `entity_type` ＋ `entity_id` |
| 資料存取與異動內容 | `before_data` / `after_data`（JSON 前後值） |
| 帳號與權限變更 | `project_membership.*`、`project_party.*` 等事件類型 |
| 登入名稱 | 由 `actor_user_id` 對應至帳號；登入事件另存於 `auth.audit_log_entries` |

## 二、保留期間

1. **保留期間至少六個月**，且**本服務未設置任何自動清除或輪替機制**——
   稽核資料在契約存續期間內持續保存，不會因時間而被系統刪除。
2. 契約終止後的處理依委外契約與個資委外附約辦理（資料返還、刪除與切結）。
3. 機關另有更長保存年限要求者，於契約載明後依機關規定辦理。

---

## 三、完整性與正確性怎麼保證（這是「確保完整與正確」那句話的實作）

1. **伺服器端產生，前端無法偽造**：稽核事件由資料庫觸發器在與資料異動**同一個交易**內寫入；
   IP 位址由伺服器端從請求標頭解析，**不接受前端傳入參數**。
2. **Append-only**：稽核表沒有 UPDATE／DELETE 政策，且資料表權限已 `revoke`；
   即使以服務端金鑰連線也不能改寫歷史（觸發器會 raise）。
3. **存取受限**：稽核表啟用資料列層級安全性（RLS），僅該專案成員可讀；
   跨租戶的營運紀錄僅平台管理員可讀。
4. **唯一的移除路徑是專案刪除**（客戶主動要求刪除資料時的級聯刪除），
   而**該刪除行為本身會留痕**於 `project_deletion_records`（不掛外鍵、append-only），
   記錄誰、於何時、刪除了哪個專案、以及**刪除當時該案的稽核事件筆數**。
   → 因此「日誌被移除」這件事永遠有跡可循，不會靜默消失。
5. **測試釘住**：上述行為以 pgTAP 自動化測試驗證（稽核 append-only、IP 解析規則、
   刪除留痕與其 append-only 性質），每次變更都會重跑。

## 四、稽核人員可以怎麼驗證（可現場執行）

```sql
-- 各稽核表最舊與最新一筆、總筆數（證明實際保存區間）
select 'audit_events' as log, min(occurred_at), max(occurred_at), count(*)
  from audit_events
union all
select 'agent_actions', min(created_at), max(created_at), count(*) from agent_actions;

-- 任一事件的完整可歸責欄位（含 IP）
select occurred_at, actor_user_id, actor_project_role, actor_ip,
       event_type, entity_type, entity_id
  from audit_events order by occurred_at desc limit 20;

-- 專案刪除留痕
select deleted_at, project_name, deleted_by, audit_event_count
  from project_deletion_records order by deleted_at desc;
```

## 五、責任與檢視

- 本政策由服務提供商負責人維護，**每年檢視一次**，或於法規、架構變更時即時修訂。
- 日誌處理若發生失效（寫入失敗、儲存不足），依漏洞回報與應變機制之流程處理並通知受影響機關。
- 資安事件通報窗口與流程見公開頁面 `/#/security`。

## 附註：與「資料刪除義務」的關係

保留六個月是**服務期間內**的稽核要求；
契約終止或機關要求刪除個人資料時的刪除義務，是**另一件事**，依附約辦理。
兩者不衝突——刪除時會留下刪除紀錄，既滿足刪除義務，也保留可歸責性。

## 1. 結論先講

目前產品**不需要砍掉重寫**，也不缺主要工程功能。真正造成「亂」的原因有四個：

1. **初次使用有兩條互相矛盾的路**：建案後前往標單，但 Dashboard 又要求先去專案文件。
2. **AI 有三個重疊入口**：`/agent`、全站浮動 Copilot、未列在導覽的 `/assistant`。
3. **相同概念保留兩套資料模型**：`requirements`／`contract_obligations`、`project_members`／`project_memberships`。
4. **少數重要寫入不是原子操作**：標單清空與分批匯入可能半成功，這比畫面整理更應優先處理。

建議現在先停止增加新功能，依序完成：

```text
Git 基準
  → 標單資料安全
    → 單一初次使用流程
      → 單一 AI 體驗
        → 成員與正式模式
          → 一次處理一項架構債
```

## 5. 從頭走一次目前產品

### 5.1 帳號與進案

目前流程：

```text
公開註冊
  → 使用者自己選廠商／監造／機關
    → 建立專案
      → 自動前往「標單工項」
```

問題：

- 專案角色由註冊者自行選擇，正式進案時沒有邀請方再次確認身分。
- 邀請只能加入已註冊帳號；對方必須先註冊且先選對組織別。
- 沒有「待接受邀請」狀態，也沒有邀請先行流程。
- 建案完成後立即前往 `/boq`，與 Dashboard、BOQ 頁面現在主張的「先到專案文件一次上傳」不一致。

### 5.2 專案初始化

產品目前同時暗示兩種初始化方式：

```text
A. 建案 → 標單工項 → 匯入 PCCES
B. 建案 → 專案文件 → 一次上傳標單、契約、規範與圖說
```

文件優先的方向比較完整，因為期限、成員、驗收與 Requirement 本來就不該依賴 BOQ 才能開始。但 `/agent`、`/assistant` 與多個工作頁仍在 BOQ 未匯入時整頁擋住。

建議唯一流程：

```text
建立專案
  → 確認三方成員
    → 上傳專案文件（含 PCCES）
      → 檢查自動分類與 AI 建議
        → 開啟正式模式
          → 進入日常履約
```

### 5.3 日常履約

廠商、監造、機關的主要業務模組大致齊全：日誌、估驗、付款、進度、品質、工安、送審、RFI、變更、驗收、活動紀錄及跨案總覽。

問題不在缺模組，而在入口層次：

- 側欄有 9 個主要入口，各工作台再展開最多 5 個分頁。
- 「Agent、Dashboard、提醒中心」都在呈現今天該做的事，但提醒中心被隱藏。
- 風險稽核被隱藏，只能靠 Agent 或深連結。
- 施工日誌曾因「Agent 可以做」而被隱藏，實測後才恢復，證明目前導覽收斂原則曾經過度依賴 AI 可發現性。

簡化方向不是再藏更多頁，而是：

- Agent／首頁回答「今天做什麼」；
- 工作頁回答「我要親自填、查、審什麼」；
- 每一個 Agent 結果都能直接連到唯一人工工作頁。

### 5.4 AI 體驗

目前有三套使用者可接觸的 AI 問答：

| 入口 | 後端功能 | 對話記憶 | 現況 |
|---|---|---|---|
| `/agent` | `agent.run` | 前端保留最近對話 | 主要入口、導覽可見、含草稿收件匣 |
| 浮動 Copilot | `agent.run` | 不帶 history | 全站可見，但只在已匯 BOQ 後出現 |
| `/assistant` | `assistant.chat` | 獨立問答 | 導覽未列，但路由仍可直接進入 |

這會讓使用者無法判斷三者能力、記憶與權限是否相同，也讓平台維護兩個功能開關與兩支 Edge Function。

建議定案：`/agent` 是唯一完整 AI 產品；浮動按鈕只做同一 Agent 的快速入口；`/assistant` 確認沒有獨有能力後改為導向 `/agent`。

## 8. 建議的最小產品結構

這是資訊架構方向，不是要求一次重畫全部 UI。

```text
今天
├── Agent
└── 我的待辦／風險

專案設定
├── 專案文件
├── 三方成員
└── 標單工項

履約作業
├── 施工日誌
├── 品質與工安
└── 契約與協作（Requirement／送審／RFI／變更）

財務與結案
├── 估驗與金流
└── 驗收結算

監督
├── Dashboard／跨案總覽
└── 活動紀錄／稽核
```

原則：

- 先調整入口與文案，不先搬檔案或拆新模組。
- 人工工作頁必須可找到；Agent 不能成為唯一入口。
- 同一件事只保留一個主要頁面；其他入口只做 deep link。
- 不新增第四種角色、不新增 repository 層、不建立 GovAgent 外掛 DSL。

## 9. 給 Fable 5 的分批工作包

範圍：

- 先提交／push 最新文件。
- 三方角色程式另成一個 commit。
- Fable 5 從新 branch 開始，每個工作包一個 PR。

### W1｜標單資料安全

範圍：只處理 P0-01、P0-02。

不要順便重做 BOQ UI、解析器或資料模型。

完成條件：失敗注入測試證明重設與匯入都是全成或全敗；原有 494 Vitest、12 E2E 與相關 pgTAP 通過。

### W2｜單一初始化流程

範圍：建案成功導向、初始化清單、無 BOQ 時的 Agent／頁面提示。

不要新增 onboarding framework；用現有頁面和一個簡單 checklist 即可。

完成條件：新帳號能依同一條路完成建案、成員、文件、BOQ、正式模式；所有空狀態指向同一下一步。

完成條件：三方權限說明與實際 `can`／RLS 一致；邀請錯誤可理解、可重試；正式模式前能清楚確認三方是否到齊。

### W5｜一次一項架構債

依序處理 C-001、C-002、C-003；每次只選一項，先盤點資料與 rollback，再取得實作核准。

完成條件：不是「檔案變少」，而是同一業務概念只有一個權威來源，舊資料仍可追溯。

### W6｜最小真案驗收

範圍：保留快速 demo E2E，新增少量真 Supabase 關鍵鏈：

1. 註冊／登入／加入專案／正式模式。
2. 廠商提送 → 監造審核 → 機關核准／付款。
3. 文件上傳 → Requirement 建議 → 人工核定。
4. 標單匯入失敗與重設失敗的 rollback。

完成條件：不以 demo 通過代替真實 RLS、RPC、Storage 與 Edge 驗證。

## 10. 開發前需要使用者定案的五件事

| 決策 | 建議預設 | 未定案前不要做 |
|---|---|---|
| 建案後第一站 | 專案文件 | 不要同時維護 BOQ-first 與 contract-first onboarding |
| 主要 AI 入口 | `/agent` + 薄浮動入口 | 不要繼續擴充 `/assistant` |
| 正式專案角色來源 | 邀請／專案管理者確認 | 不要把公開自選角色視為正式身分驗證 |
| AI 功能開關故障策略 | fail-closed | 不要讓 kill switch 在 DB 錯誤時自動失效 |
| Requirement／obligation | 先做資料盤點，再決定單向或解耦 | 不要直接刪 trigger、表或歷史資料 |

## 11. 不建議做的事

- 不重寫 React／Supabase 技術棧。
- 不因為檔案多就先搬資料夾。
- 不建立第四、第五種專案角色。
- 不把所有頁面查詢強迫搬進 Store 或 repository。
- 不再用「Agent 做得到」作為隱藏人工入口的唯一理由。
- 不一次處理兩套成員模型、兩套 Requirement 模型與 Demo 同步。
- 不在 Git dirty worktree 上讓多個 AI 同時改同一批檔案。
